SESSION 02 · BITE · AUTHORISING DEVICES IN FAZ

Establish the Relationship, Then Rely on It

Four steps to onboard a FortiGate into FortiAnalyzer — and the symptom card for when it goes wrong.

Steps one to three are things you did. Step four is the only one that's evidence.

Every later Round 1 task — indicators, feeds, policy, enforcement — stands on this pipe. If it's empty, everything downstream scores nothing.

SECTION 01

The Onboarding Order — and How to Do It

Do these in sequence. Each one alternates which box you're standing at: Gate, then FAZ, then FAZ, then back to the Gate.

  1. 1
    FortiGate points its log settings at FAZ
    ON THE FORTIGATE
    Go to Security Fabric > Fabric Connectors, open the FortiAnalyzer Logging card, and set the FAZ IP address. A warning appears saying the FortiGate is not yet authorized on the FortiAnalyzer — that's expected here. Authorisation is done on the FAZ side, next step. The Gate is now generating and sending; nothing is landing yet.
  2. 2
    Authorize the device in FAZ
    ON THE FORTIANALYZER
    Go to Device Manager > Unauthorized. Select the FortiGate(s) and click Authorize. They move to the authorized list, and FAZ starts accepting logs. Until this moment, logs are refused, not queued. Onboarding a whole Security Fabric group? All devices in the group must be added — and added to the same ADOM.
  3. 3
    Clear the warning on the root FortiGate
    ON THE FORTIANALYZER
    After authorising, a warning icon appears beside the root FortiGate only — not the downstream ones. Click it and enter the root FortiGate's admin username and password. This is a separate permission: it lets FAZ log into the Gate and read the Security Fabric topology, which is configuration data, not log data. Fortinet recommends a dedicated Super_User account on the FortiGate with read-only access to System Configuration and None elsewhere, so FAZ activity is identifiable in the logs.
  4. 4
    Verify from the FortiGate side
    ON THE FORTIGATE
    Back on each Gate: Security Fabric > Fabric Connectors, double-click the FortiAnalyzer Logging card, and confirm storage usage information is shown. Storage usage is a value only FAZ can supply — the Gate has no way to invent it. A green status is a state the Gate holds on its own; a returned disk figure is a reply. If storage usage is absent, treat the device as not onboarded, whatever the authorized list says.
🧠
MENTAL MODEL
Establish the relationship before relying on the information. Configured is intention — verified is truth.
🥊 FROM THE GYM
You can walk into the cage without checking in at the front desk. You'll still throw hands, you'll still sweat — but there's no record of a fighter, so there's no record of a fight. Sign in first. Then prove you signed in.
SECTION 02

Symptom Card — What You See vs What You Check

Same discipline every time: name the sender and the receiver before you diagnose. Then find the row.

What you see What it means Check
Device sits in Unauthorized FAZ refuses the logs. They aren't queued — they're gone Authorize it
Authorized, but Log View empty Two possible causes Right device? Then encryption levels
Authorized, storage usage not showing The Gate has no reply from FAZ. Relationship unproven Treat as not onboarded
Warning icon on root FortiGate FAZ can't log in to read the fabric Supply root admin credentials
Logs indexing, no fabric topology Log trust ≠ admin access Same as above — the reverse door
Green status, nothing else checked A light, not evidence Go get storage usage
The encryption row. Logs travel over OFTP, encrypted. FAZ's encryption level must be equal to or lower than the sending FortiGate's. FAZ set higher than the Gate refuses the logs — same symptom as an authorisation problem, entirely different fix.
ENCRYPTION LEVEL — WHERE IT LIVES
# On the FortiAnalyzer
config system global
    set enc-algorithm {high | low | medium}
end

# On the FortiGate
config log fortianalyzer setting
    set enc-algorithm {high-medium | high | low}
end
SECTION 03

The Two Distinctions to Carry In

Direction. The Gate sends. FAZ receives. Name those two before you diagnose anything — knowing the right components is not the same as knowing which way the arrow points.
Doors. Logs flow Gate → FAZ on authorisation. Topology flows FAZ → Gate on admin credentials. Separate permissions, separate failures, separate symptoms. One door open doesn't mean both.
🎯
COMMON UFC TRAP
Under pressure, the arrow gets reversed. "Unauthorized" doesn't stop FAZ sending to the Gate — it stops FAZ accepting from the Gate. Fix sender and receiver first, every time.
