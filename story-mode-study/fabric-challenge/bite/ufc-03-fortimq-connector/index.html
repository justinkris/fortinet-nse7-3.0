UFC-03 · BITE · FORTIMQ CONNECTOR

FortiAnalyzer Sends, FortiGate Retrieves

A cloud service, not an appliance. Enabling it proves nothing on its own.

A green connector tick proves one hop of a five-hop chain.

Everything on this page exists to keep you from mistaking a dispatch receipt for an enforcement result.

01 · Concept

What FortiMQ Actually Is

FortiMQ is a cloud service. There is no appliance. What you configure is the FortiMQ Connector on FortiAnalyzer, introduced in FortiAnalyzer 8.0.0. When you enable it, the connector automatically establishes a connection to the FortiMQ cloud service — no additional configuration is required inside FortiAnalyzer.

Its job is narrow and specific: direct transmission of blocked indicators from FortiAnalyzer to FortiGate devices. Before 8.0.0, block lists could only be distributed to FortiGates using the FortiManager connector. FortiMQ gives you that capability without a FortiManager deployed in the environment.

Three fixed properties. The FortiMQ connector is present and disabled by default in all Fabric and FortiGate-type ADOMs. You cannot create a new one. You cannot delete the existing one. It is a fixture of the ADOM — you only ever turn it on.

The information chain

FortiAnalyzer sends. FortiGate retrieves. The arrow direction is the thing people get backwards.

Once you block an indicator, the block_indicator playbook runs in the background on FortiAnalyzer and sends the indicators to FortiMQ. FortiGate retrieves those indicators from FortiMQ and updates them in its external feeds. Those feeds can then be used in policies or profiles to deny access.

Corner Note
Wraps on, gloves on, mouthguard in. That's the connector enabled. Nobody has thrown a punch yet.

02 · Prerequisites

Four Things Must Be True — Enabling Is Only One

Enabling the connector is a single item on a four-item list. Three of the four live outside the connector card, and two of them live on a different device entirely. This is why a green tick on FortiAnalyzer can coexist with an empty feed on the FortiGate.

RequirementWhereWhy it matters
Logging enabled from FortiGate devices to FortiAnalyzer FortiGate → FortiAnalyzer Establishes the device relationship the whole workflow assumes.
Both devices registered under the same FortiCare account Both Stated requirement for proper communication and integration. Entitlement / identity boundary.
Cloud-based Fabric Feed synchronization enabled and configured FortiGate Without it the Gate never consumes or enforces the block indicators it is being sent.
FortiMQ Connector enabled FortiAnalyzer Turns on the ADOM's connection to the FortiMQ cloud service.
Unverified The mechanism behind the shared FortiCare account — whether it acts as a cloud tenancy boundary — is not stated in the supplied material. The requirement itself is sourced; the reason is inference. Requires official Fortinet source verification.

03 · Configuration Reference

Turning It On, and Using It

Enable the connector

  1. Go to Incidents & Alerts > Automation > Active Connectors and enable the FortiMQ Connector.
  2. Confirm the connector status. The status reflects its health — whether the API connection is successful.
Connector status colours. Green — the API connection is successful. Orange — the API connection is unknown. Red — the API connection is down. Read this as FortiAnalyzer's connection to the cloud service, nothing further downstream.

Block an indicator

With the connector active, the Block action is available in:

  • Incidents & Alerts > Indicators
  • Incidents & Alerts > Incidents > Incidents
  • Incidents & Alerts > Incidents > Incidents > Incident Analysis
  • Log View — right-click an ip, url, domain, or mac-address in table or detailed view and choose Create indicator and block. This adds a new indicator and blocks it automatically.

Hovering over Block with the FortiMQ connector active displays the tooltip: Block/Unblock will be carried out by FortiMQ connector. If neither connector is set up or active, the Block option is greyed out in the Incidents and Indicators panes.

Unblock and status tracking

Selecting a blocked indicator in Incidents & Alerts > Indicators makes Unblock available in the toolbar and shortcut menu. The same pane carries a pie chart and a Block Status column with three values: TBD, Blocked, Unblocked.

Read this column carefully. On the FortiMQ path, Blocked means the block_indicator playbook ran and handed the indicator to FortiMQ. That is a dispatch receipt. It is not proof of retrieval, and it is not proof of enforcement.

04 · Comparison

FortiMQ vs FortiManager

Both connectors can distribute blocked indicators. They differ in scope, in priority, and in what their status actually claims — and the differences are exactly where a challenge question lives.

FortiMQ ConnectorFortiManager Connector
Scope ADOM-specific. Blocked indicators apply only to FortiGates in the same Fabric or FortiGate ADOM in FortiAnalyzer. Global. Operates at a global level.
Priority when both active Wins. Blocking is carried out by FortiMQ. Still supported, but indicators are sent this way only if the FortiMQ connector is disabled.
Setup burden Enable only — connects to the cloud service automatically, no additional configuration in FortiAnalyzer. Requires a FortiManager deployed in the environment.
Status progression Block Status shows Blocked. Shows Blocked (Pending) first; the block_indicator playbook runs every five minutes, then status changes to Blocked.
What "Blocked" confirms Indicator handed to FortiMQ. FortiGate must still retrieve it. The list is updated on FortiManager — explicitly not synced to the FortiGate.
Where it lands FortiGate external feeds, pulled from FortiMQ. FortiManager External Resource list, named <FAZ ADOM name>-BLK<indicator-type> — e.g. root-BLKIP.
Version constraint None stated. FortiManager firmware version must match FortiAnalyzer for the block list to be pushed to FortiGates.
The habit that costs you. FortiManager was global. FortiMQ is not. Right indicator, right connector, wrong ADOM — and the FortiGate you are staring at was never in scope for that block. It is not a fault. It is expected behaviour.
🧠
Mental Model
Priority is decided by whether FortiMQ is disabled — not by whether it is healthy.
05 · Verification & Troubleshooting

One Look That Splits the Chain

Three separate claims hide inside the sentence "the indicator is enforced." Each is proven in a different place, and collapsing them is the single most common failure of reasoning on this topic.

ClaimProven whereEvidence
DispatchedFortiAnalyzerBlock Status shows Blocked; block_indicator playbook ran.
RetrievedFortiGateIndicator present in the external feed.
EnforcedFortiGateFeed referenced in a policy or profile, and traffic actually denied.
Highest-value single check: the external feed on the FortiGate. It bisects the chain. If the indicator is in the feed, the send and the retrieve are both cleared in one glance and you are down to enforcement. If it is not, enforcement is irrelevant and you are hunting upstream.

Scenario matrix

SymptomWhat it rules outInspect first

Status Blocked, feed on FortiGate empty Enforcement — irrelevant until the indicator arrives Cloud-based Fabric Feed synchronization on the FortiGate; then FortiCare account match across both devices.
Status Blocked, feed empty, connector green The FortiAnalyzer-to-cloud hop only The Gate's side. Green covered one hop and said nothing about entitlement or the Gate's willingness to pull.
Feed populated, traffic still allowed Send and retrieve — both proven Whether the feed is referenced in a policy or profile. A list nothing points at denies nothing.
One FortiGate enforces, another does not Send, retrieve and enforcement on the working device ADOM membership. FortiMQ is ADOM-specific — the second Gate may never have been in scope.

No diagnostic in the supplied material distinguishes them — you inspect the configuration state directly on each device. Any finer-grained separation requires official Fortinet source verification.

06 · Fast Recall

The Nine Things Worth Carrying In

  • FortiMQ is a cloud service. The connector lives on FortiAnalyzer. There is no FortiMQ connector on the FortiGate.
  • Introduced in FortiAnalyzer 8.0.0; disabled by default in all Fabric and FortiGate-type ADOMs.
  • You cannot create or delete it — only enable it.
  • Enabling requires no additional configuration in FortiAnalyzer.
  • Chain: FortiAnalyzer → FortiMQ → FortiGate retrieves → external feed → referenced in policy/profile → deny.
  • Four prerequisites; two live on the FortiGate.
  • FortiMQ is ADOM-specific; FortiManager is global.
  • FortiMQ takes priority; FortiManager carries indicators only if FortiMQ is disabled.
  • Connector status = FortiAnalyzer's API connection to the cloud service. Nothing more.
