💭 THINK FIRST · STORY & PROBLEM

Racks' offhand comment reopens a thread nobody has looked at since EP-01: the implicit rule has quietly handled every non-Teams packet at Tuggers the entire time. No incident is forcing this review — that's exactly what makes it a genuine architecture exercise rather than a fire drill.

  • If nothing matches any explicit SD-WAN rule, what actually chooses the outgoing member — a separate mechanism, or the same one with a different input?
  • Both port1 (500Mb) and port2 (200Mb) are Alive and Good — zero degradation anywhere. What kind of problem could still exist under those conditions?
Q1 — MODEL ANSWER
The implicit rule is the same session-birth decision + session-caching mechanism as any explicit rule — it just uses a different, zone-level setting (load-balance-mode) instead of a rule strategy field.
Q2 — MODEL ANSWER
A capacity-blind distribution problem: source-ip-hash splits sessions roughly evenly by count, ignoring that port2 (200Mb) has far less headroom than port1 (500Mb) — so port2 saturates proportionally faster even with perfect health and quality.

No incident triggered this episode. Dave "Racks" O'Connor simply noticed that every SD-WAN rule at Tuggers — the Teams/ISDB rule from EP-01 — matches one specific traffic type. Everything else (web browsing, file shares, general SaaS) has always fallen through to whatever handles unmatched traffic, and nobody has ever actually examined what that is or how it decides.

The current state is deceptively calm: port1 (500Mb) and port2 (200Mb) are both Alive and Good — no SLA failures, no degradation. That absence of symptoms is exactly why this episode matters: the failure mode this episode uncovers doesn't need a bad link to exist.

Common misconception: "If both members are healthy, the load-balancing method doesn't matter." Health (Alive/Good) and capacity-awareness are two completely separate properties of a distribution method — a method can be perfectly healthy-aware and still be totally capacity-blind.

💭 THINK FIRST · IMPLICIT RULE MODEL

EP-03 established that explicit-rule sessions "choose once, cache forever." Does that model actually apply to traffic that never matched an explicit rule at all — or is the implicit rule doing something structurally different?

  • What two conditions must a member satisfy before it is even eligible to be selected by the implicit rule?
  • Does inserting or reordering SD-WAN rules (e.g. via FortiManager) ever move an already-established session onto a different rule's statistics?
Q1 — MODEL ANSWER
Alive (health-check) AND a valid FIB route (interface + next-hop). Neither is sufficient alone — a healthy member with no route can't forward, and a routed member that's Dead is excluded regardless.
Q2 — MODEL ANSWER
No. Rule table changes only affect NEW sessions evaluated after the change. An existing session's cached forwarding decision only moves for the two EP-03 triggers: manual/admin session clear, or a genuine FIB/route change. Reordering matches neither.
SECTION 02

Same Mechanism, Different Input

The implicit rule is not a separate, dumber fallback mechanism. It uses exactly the same session-birth decision and session-caching model built in EP-03's "front desk / access card" analogy — the difference is only in what decides the member, not when or how often that decision is made.

  • Explicit rule: matching criteria (e.g. ISDB) + a rule strategy (Manual, Best Quality SLA, Lowest Cost SLA, Maximize Bandwidth SLA), configured per-rule.
  • Implicit rule: catches anything matching no explicit rule, governed by a single zone-level setting called load-balance-mode — configured once for the whole zone, not per traffic type.
Eligibility (both required, always): a member must be Alive (health-check reachability) and have a valid FIB route (interface + next-hop) before it can be selected by the implicit rule. Health-check status alone is never sufficient.

Remember: Rule insertion or reordering (even via FortiManager push) can only change what a brand-new session would be assigned. It never reaches back into the session table to re-stamp an existing session onto a different rule's hit-count — that would require one of the two EP-03 triggers (manual clear or FIB/route change), and reordering is neither.

💭 THINK FIRST · LOAD-BALANCE MODES

Source-ip-based splits new sessions roughly evenly by count. Port1 is 500Mb and port2 is 200Mb — a fixed, permanent, known ratio. Which distribution mode actually accounts for that ratio, and does it need to measure anything live to do it?

  • What's the real difference between weight-based and usage-based — and which one fits a capacity ratio that never changes?
  • Is a specific new session ever guaranteed to land on the highest-weighted member under weight-based mode?
Q1 — MODEL ANSWER
Weight-based uses a static, admin-configured ratio — no live measurement required. Usage-based dynamically measures real-time throughput against configured bandwidth. Since 500:200 never changes, weight-based is the simpler, correct fit.
Q2 — MODEL ANSWER
No. Weight-based is a proportional guarantee across many sessions (e.g. ~5/8 to port1, ~2/8 to port2 on a 5:2 ratio), not a guarantee for any single new session. This aggregate-vs-individual distinction is a classic exam trap.
SECTION 03

Three Ways to Split New Sessions

load-balance-mode is configured under config system sdwan at the zone level and controls how the implicit rule distributes new sessions among eligible members. None of its options consult SLA compliance — that's exclusively an explicit-rule-strategy behaviour.

ModeWhat it optimizes forBest fit
source-ip-based (default)Session-count fairness by source-IP hash — blind to capacity AND SLASmall, symmetric links only
weight-basedStatic, admin-configured ratioFixed, permanent, known capacity differences
usage-basedLive-measured throughput vs configured bandwidthCapacity or conditions that fluctuate (e.g. variable-rate backup links)
Exam tip: Source-IP hashing exists so that all packets in the same session (and typically the same source) keep landing on the same member — this is what prevents mid-session member-flapping from breaking a connection or causing out-of-order delivery, not a load-balancing quality feature.
Common misconception: "Weight-based guarantees the new session goes to the highest-weighted member." It only guarantees a proportional split over many sessions — any single session can still land on any eligible member.
Remember: Explicit-rule strategies (Manual / Best Quality SLA / Lowest Cost SLA / Maximize Bandwidth SLA) and implicit-rule load-balance-mode (source-ip-based / weight-based / usage-based) are separate, non-overlapping tool sets. An explicit catch-all rule cannot access weight-based or usage-based distribution — those only exist at the zone level for the implicit rule.
🧠
MENTAL NOTE
Ask "is the underlying condition fixed or variable?" first. Fixed → weight-based. Variable → usage-based. Neither ever considers SLA/quality — that's an explicit-rule-only concept.

SECTION 04

Proving It at the Command Line

Reasoning through the model is necessary but not sufficient at architect level — you need to know which command actually surfaces the evidence, and what to look for in its output.

FortiOS CLI — diagnose sys sdwan member (illustrative structure)
# Shows each SD-WAN member's status, and — depending on the configured
# load-balance-mode — session/volume counts or measured throughput
# against configured bandwidth. Field names vary slightly by FortiOS
# build; this shows the shape of what to look for, not a literal capture.

Member(1): interface(port1), zone(wan1-zone)
  status: alive, sla: 0x1 (all targets met)
  configured-bandwidth: 500 Mbps
  measured-throughput:  180 Mbps  (36% of configured capacity)
  active-sessions:      412

Member(2): interface(port2), zone(wan1-zone)
  status: alive, sla: 0x1 (all targets met)
  configured-bandwidth: 200 Mbps
  measured-throughput:  140 Mbps  (70% of configured capacity)
  active-sessions:      388

Anatomy: the session counts (412 vs 388) look almost even — exactly what source-ip-based produces. But measured-throughput as a percentage of configured-bandwidth tells the real story: port2 is at 70% capacity while port1 sits at 36%, despite carrying fewer sessions. That percentage gap — not the raw session count — is the proof of capacity-blind saturation.

FortiOS CLI — diagnose sys session list (illustrative excerpt)
# A session matched by an EXPLICIT SD-WAN rule shows these fields:
sdwan_mbr_seq=1 sdwan_service_id=1

# A session forwarded via the IMPLICIT rule / standard FIB routing
# does NOT show these fields at all — their absence is itself the
# evidence that this session never touched an explicit SD-WAN rule.
FortiOS CLI — diagnose firewall proute list (illustrative excerpt)
# Policy routes derived from SD-WAN rules carry a route ID above 65535
# and include vwl_service / vwl_mbr fields identifying the originating
# SD-WAN rule and the member it steers to.

id=65537  vwl_service=1  vwl_mbr=1  dst=0.0.0.0/0  gwy=... hit_count=18420

💭 THINK FIRST · EXAM TRAPS & TOPOLOGY

Could you avoid all of this by just adding one explicit rule at the bottom that matches everything? It's a fair architect instinct — but there's a real, exam-relevant reason it doesn't fully substitute.

  • What can load-balance-mode do that no explicit-rule strategy can?
Q1 — MODEL ANSWER
Weight-based and usage-based distribution — a catch-all explicit rule is limited to Manual / Best Quality SLA / Lowest Cost SLA / Maximize Bandwidth SLA, none of which distribute purely by static or live capacity ratio.
SECTION 05

Why Not Just Build a Catch-All?

A genuinely good architect instinct: add an explicit rule matching all sources/destinations/services at the bottom of the rule table, and never touch the implicit rule again. It's structurally valid — nothing stops you.

But it costs you something specific: explicit rules only ever use rule strategies. load-balance-mode's weight-based and usage-based options are zone-level settings that exist only for the implicit rule. Build the catch-all, and you're stuck choosing between Manual (preference order, ignores load entirely) or an SLA-aware strategy (cares about link quality, not raw capacity ratio) — losing the exact tool this episode built for a pure capacity-distribution problem.

Exam trap: "The implicit rule can be bypassed entirely by adding a catch-all explicit rule, achieving identical flexibility." False — you lose access to weight-based/usage-based distribution, which have no explicit-rule equivalent.

Key takeaways:
  • The implicit rule uses EP-03's exact session-caching model — only the selection input differs.
  • Eligibility always needs Alive and a valid FIB route — never one alone.
  • Weight-based = static/fixed ratio; usage-based = live/variable measurement; neither considers SLA.
  • Explicit-rule strategies and load-balance-mode are separate tool sets — a catch-all rule can't borrow the other's options.
  • Rule table reordering is never a re-evaluation trigger for existing sessions — only manual clear or FIB/route change qualify.
