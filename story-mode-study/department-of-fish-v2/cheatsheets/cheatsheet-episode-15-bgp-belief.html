💭 THINK FIRST · FOUR STAGES

A BGP update crosses four separate gates before it can carry traffic, and each gate has its own failure mode and its own instrument. Most engineers check the routing table, find nothing, and start guessing. The discipline is to check the gates in order.

  • Name the four stages a prefix passes through, and the one command that proves each.
  • You run received-routes and get nothing back. What have you proved?
Q1 — MODEL ANSWER
Received (… received-routes), accepted (… routes), selected (get router info bgp network <prefix>), installed (get router info routing-table <prefix>).
Q2 — MODEL ANSWER
Nothing — unless soft-reconfiguration is enabled inbound on that neighbour. Without it the device never retained a pre-policy copy, so an empty output is evidence of a missing prerequisite, not a missing advertisement.
SECTION 02 · THE CORE MODEL

Four Stages, Four Instruments

StageQuestion it answersCommandTypical cause of failure
ReceivedDid the update arrive on the wire?get router info bgp neighbors <ip> received-routesPeer never advertised it; outbound filter at the sender
AcceptedDid inbound policy let it into the BGP table?get router info bgp neighbors <ip> routesInbound route-map / prefix-list deny; max-prefix; AS-path loop
SelectedDid it win best-path within BGP?get router info bgp network <prefix>Next hop inaccessible; lost on local-pref / AS path / MED
InstalledDid it beat other protocols into the RIB?get router info routing-table <prefix>Another protocol holds a lower administrative distance
ForwardedIs traffic actually using it?diagnose sys session listExisting sessions pinned to the old path
The vantage-point trap. "Did it leave?" and "did it arrive?" are different questions asked in different places. received-routes is run at the receiver and needs set soft-reconfiguration enable inbound. advertised-routes is run at the sender and needs no prerequisite at all. When you cannot enable soft-reconfiguration on a production box, go to the sender.
FortiOS CLI · the four instruments
#  Stage 1 — received (pre-policy)  [prerequisite below]
get router info bgp neighbors 10.255.0.1 received-routes

config router bgp
    config neighbor
        edit "10.255.0.1"
            set soft-reconfiguration enable
        next
    end
end

#  Stage 1 alternative — ask the SENDER what it sent
get router info bgp neighbors <spoke-loopback> advertised-routes

#  Stage 2 — accepted (post-policy, in the BGP table)
get router info bgp neighbors 10.255.0.1 routes

#  Stage 3 — selected (best-path within BGP)
get router info bgp network 10.90.0.0/16

#  Stage 4 — installed (in the RIB)
get router info routing-table 10.90.0.0/16
get router info kernel                      # the FIB view
Reading stage 3 output. A selected path shows the > marker. no best path alongside entries that look healthy is the signature of disqualification — almost always (inaccessible).
Analogy

A job application, not a race.

  • Received — the application reached the building.
  • Accepted — HR did not bin it at the door.
  • Selected — it beat the other applicants for the same role.
  • Installed — it beat the internal candidate the other department already had lined up.

MENTAL NOTE

💭 THINK FIRST · NEXT HOP

Brisbane's BGP table held two paths for the Fisheries range. Both were marked valid, internal. Neither won. Nothing about the attributes was wrong — the contest never happened.

  • How can a path be valid and still be unusable?
  • Where did a next hop that only the hub can reach come from, and which device should fix it?
Q1 — MODEL ANSWER
valid describes policy acceptability, not reachability. If the recursive lookup for the next hop fails, the path is disqualified before best-path selection runs and its attributes are never compared.
Q2 — MODEL ANSWER
Redistribution carried the OSPF next hop into BGP, and iBGP does not rewrite NEXT_HOP in transit. Fix it at the advertiser with set next-hop-self enable — the layer that authored the fault.
SECTION 03 · ROOT CAUSE

BGP Does Not Forward to a Next Hop — It Resolves One

Brisbane · the evidence
Brisbane # get router info bgp network 10.90.0.0/16

BGP routing table entry for 10.90.0.0/16
Paths: (2 available, no best path)
  Local
    172.31.250.2 (inaccessible) from 10.255.0.1 (10.255.0.1)
      Origin incomplete, metric 0, localpref 100, valid, internal

  Local
    172.31.251.2 (inaccessible) from 10.255.0.2 (10.255.0.2)
      Origin incomplete, metric 0, localpref 100, valid, internal

Origin incomplete was the tell. It means the prefix entered BGP by redistribution, not by a network statement. Something at the hub authored these attributes.

Origin codeShown asMeaning
IGPinetwork statement — typed into BGP deliberately
EGPeLegacy EGP. Historical, effectively extinct
Incomplete?Redistribution — arrived from another protocol
Origin sits low in the best-path order — well below weight, local preference and AS path — so it rarely decides anything. Its real value is forensic: it tells you a redistribution point authored the route.

The causal chain. The hubs learn the Fisheries prefixes via OSPF, where the next hop is legitimately the Fisheries core across the tunnel. Redistribution into BGP carries that IGP next hop unchanged. iBGP does not rewrite NEXT_HOP as updates propagate between internal peers. So every spoke inherited 172.31.250.2 — a transit address that exists only at the hub.

Why every other prefix worked. All iBGP peerings are sourced from loopbacks in one contiguous pool, and every spoke carries a summary route for that pool pointing at the overlay zone. One route resolves every present and future peer. The Fisheries transit addresses are not loopbacks and not in the pool — nothing covered them.

FortiOS CLI · the fix, at both hubs
config router bgp
    config neighbor
        edit "10.255.1.20"
            set next-hop-self enable
        next
    end
end

#  On a hub acting as route reflector, for reflected routes:
#      set next-hop-self-rr enable

#  Verify from the spoke afterwards:
get router info bgp network 10.90.0.0/16
get router info routing-table 10.90.0.0/16
RemedyWhere appliedVerdict
next-hop-self at the hubs2 devicesChosen. Scales to every undelivered branch. Expresses a rule
Transit routes on every spoke60+ devices, foreverRejected. Enumerates a state, rots silently, exports DC link addressing to branches

MENTAL NOTE
Fix a fault at the layer that authored it. Two lines on two hubs, not sixty static routes on sixty spokes.

SECTION 04 · STAGE FOUR

Selected in BGP, Installed From Somewhere Else

Tuggers · 10.90.20.0/24 — best in BGP, absent from BGP in the RIB
Tuggers # get router info routing-table 10.90.20.0/24

O E2  10.90.20.0/24 [110/20] via 172.31.250.2, Fisheries-OSPF, 00:41:12

This is not a fault. When two protocols offer the same prefix, the RIB compares administrative distance and nothing else. OSPF external 110 beats iBGP 200; OSPF installs, and BGP's route sits in the BGP table marked best but uninstalled.

The exclusion that gets examined. The losing protocol's metric is never consulted. There is no comparison between an OSPF cost of 20 and a BGP path with better local preference. AD is not a tiebreaker between metrics — it is a filter applied before metrics are relevant at all.
SourceDefault ADNote
Connected0—
Static10Validated against next hop, never destination (EP-13/14)
eBGP20Beats OSPF — counter-intuitive and examinable
OSPF (incl. external)110Raised above 200 at the Department hubs as a redistribution safety net
iBGP200The overlay's distance

At Tuggers the outcome is also optimal: Tuggers is the ASBR and genuinely reaches Fisheries directly across the tunnel. Preferring an iBGP path that sends traffic to Gunners and back would be the actual fault.

🧠
MENTAL NOTE
Administrative distance filters before metrics matter. "Best in BGP but installed from OSPF" is normal behaviour, and escalating it is the mistake being tested.

SECTION 05 · NEEDS REINFORCEMENT

A Hold Timer Is Not a Withdraw

Needs Reinforcement. This was answered with the right number attached to the wrong event during the session. A recalled default that is bound to the wrong trigger produces a confident answer wrong by nearly three minutes.

The scenario. The Tuggers–Fisheries tunnel fails. Brisbane has a path via Gunners. What removes Brisbane's Tuggers path, and how long does it take?

WithdrawHold timer expiry
Triggered byA route ceasing to existA peer ceasing to respond
Session stateSession stays Established throughoutSession tears down
DurationSeconds — propagation only180 s (3 × 60 s keepalive)
This scenario✔ The tunnel died, not the peer✘ Tuggers never stopped sending keepalives
When it does applyAny prefix loss upstream of the peerBrisbane–Tuggers overlay drops with the interface still up

The actual sequence:

  1. Tunnel interface goes down → OSPF removes the Fisheries routes immediately (interface-down is a topology event, not a timer).
  2. Redistribution has nothing left to redistribute → Tuggers withdraws the prefix.
  3. Tuggers sends a BGP UPDATE carrying a withdrawn route to all iBGP peers.
  4. Brisbane deletes the path, is left with Gunners, installs it.
Why this argues for BFD (EP-18). The 180-second case is the one where the overlay itself drops while the tunnel interface stays up. That is exactly the failure BFD collapses to sub-second — and it is why BFD gets subscribed to by OSPF, BGP and static routes alike. BFD detects dead, never degraded.
🧠
MENTAL NOTE
A hold timer expires when a peer stops talking. A withdraw arrives when a route stops existing. Trace what actually failed before reaching for a timer.

SECTION 06 · CROSS-LAYER

Routing Fills the Room; SD-WAN Picks From It

With next-hop-self in place, Brisbane holds two paths to the Fisheries range with identical local preference and identical AS paths. That equality is deliberate — it is what gives the SD-WAN rule a decision to make.

RequirementWhy
set ibgp-multipath enableWithout it, only one next hop is installed regardless of equality
Equal local preferenceHighest local-pref wins outright — one candidate, no decision
Equal AS path lengthNext tiebreaker in the best-path order
Equal origin and MEDLower tiebreakers, still decisive if they differ
Both members in the SD-WAN zone with health checksSLA is the only thing that can judge quality
The tension to be able to state on demand. Local preference is how you express a routing preference — and it is exactly what destroys SD-WAN eligibility. Set localpref 200 at Tuggers and BGP decides permanently with no SLA awareness. Leave them equal and the SD-WAN rule decides continuously. You cannot have both for the same prefix. Structurally identical to EP-14's E1-versus-E2 problem.
Same model, third protocol. SD-WAN members (EP-01), OSPF equal-cost externals (EP-14), iBGP multipath (EP-15). Routing decides who is in the room. The rule decides who gets picked. ECMP is the prerequisite for eligibility, never an alternative to SD-WAN.
Retrieved cold this episode: set rfc1583-compatible enable under config router ospf. FortiGate does not load balance external OSPF routes by default; this setting makes external selection cost-only and is what permits external ECMP. E2 externals carrying the unchanged seed metric is what makes the two hub paths equal in the first place — necessary, but not sufficient without this toggle.
🧠
MENTAL NOTE
If one path wins in the routing protocol, the SD-WAN rule has nothing to choose between — and that failure looks like success until the chosen path degrades.

SECTION 07 · REVISION

Traps, Workflow and the Estate After EP-15

Troubleshooting workflow — a prefix is missing.

  1. Confirm the peer is Established. If not, this is a session problem, not a route problem.
  2. Is it in the BGP table at all? get router info bgp network <prefix>.
  3. Absent → go upstream. Ask the sender: advertised-routes. Then check inbound policy on this neighbour specifically.
  4. Present but no best path → read the next hop. (inaccessible) means recursive resolution failed.
  5. Present and marked > but not in the RIB → another protocol holds a lower AD. Confirm that is intended.
  6. In the RIB but traffic unchanged → existing sessions. Check the session table.

Common mistakes corrected this episode: assuming a filter applies estate-wide when inbound policy is per-neighbour; assuming valid means usable; reaching for the most familiar timer instead of tracing what actually failed.

  • next-hop-self enabled on both hubs' iBGP neighbours, estate-wide.

  • Unchanged: dual hub, four overlays, loopback-sourced iBGP in one private AS, Fisheries OSPF area 0 at both hubs with per-hub tags 10/20, ADVPN still deliberately disabled.
  • Still outstanding: the Fisheries prefix-list remains unwritten and unsigned.
Raised and parked. Return traffic follows the session table — reply packets do not perform a fresh route lookup and do not consult SD-WAN rules, so symmetry is automatic for an existing flow. The exposure is a new session initiated from the far end, which is an independent decision. Season 4 (EP-21, EP-22) is built on this.

Key takeaways.

  • Received → accepted → selected → installed. Four gates, four commands, no guessing.
  • BGP resolves a next hop; it does not forward to one.
  • Redistribution imports the IGP next hop. iBGP does not clean it up for you.
  • AD filters before metrics matter.
  • Withdraws are fast; hold timers are slow; they answer different questions.
  • Equal paths are the price of letting SD-WAN decide — and local preference is the thing that takes them away.
  • Fix a fault at the layer that authored it.
