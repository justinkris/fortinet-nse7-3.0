💭 THINK FIRST · THE FMG FRAME

The single most useful artefact of the season was not a feature but a filing system — four questions that give every FortiManager component a permanent place to sit.

  • What are the three copies of configuration, and which one carries traffic?
  • (1) The FortiGate's running config — the only copy that carries traffic. (2) The per-device device database on FortiManager, in the device layer. (3) Policy packages plus one shared common object database in the ADOM policy layer. Nothing reaches a FortiGate until an install runs.
Q1 — MODEL ANSWER
What is a provisioning template, structurally?
Q2 — MODEL ANSWER
An author, not a place. It is one-to-many at authoring time and one-per-device at storage time: it writes into each assigned device's own database, producing a separate complete configuration in each. That is why it overwrites hand-made edits — two authors, one page, template wins.
SECTION 02

Four questions before you touch a template

  1. Which layer am I writing into? Device layer or policy layer — they have different install operations and can disagree independently.
  2. What scope — who receives it? Assignment decides who is in the room; installation targets decide who is handed which sheet.
  3. What value goes in the field? Fixed, template default, or per-device override.
  4. What will Install Preview actually show for the worst device in the group?
Three copies of configuration
  POLICY LAYER          policy packages + one shared object DB (per ADOM)
                        installed by: Install Policy Package

  DEVICE LAYER          one device database per FortiGate
                        written by: template assignment + evaluation
                        installed by: Install Device Settings

  THE FORTIGATE         running configuration
                        the only copy that carries a packet

Capability split — heavily examinable: structured templates (System, SD-WAN, Static Route, BGP, IPsec, Certificate) vary structure via installation targets and have no logic layer at all. CLI templates have no installation targets and therefore vary structure via Jinja. Metadata variables work in both.
Why the split exists: FortiManager parses a structured template into addressable objects, so it can hang a scope field off member 3 specifically. A CLI template is unparsed text with no addressable parts — there is nowhere to attach a target, so the content must filter itself during rendering.

💭 THINK FIRST · ONBOARDING

Getting a box from a courier to a working branch without anyone driving there is a different problem from keeping it configured afterwards — and confusing the two is the season's first exam trap.

  • A branch appliance powers on with no config. Trace it to a working device.
  • Power on → discovery (DHCP option, or DNS/FortiCloud call-home) → authenticate to FortiManager by serial number → match against a pre-created placeholder object from CSV import → the placeholder's attached blueprint is pushed as initial config → device is named, addressed and minimally working with zero on-site CLI.
Q1 — MODEL ANSWER
You fix a mistake in a device blueprint. Which already-deployed devices are corrected?
Q2 — MODEL ANSWER
None. A blueprint is a one-shot snapshot applied only at the moment of ZTP provisioning, with no ongoing link back to a shared object. Templates are live shared objects — edit and reinstall and every mapped device changes. This is the key EP-07 distinction.

A single malformed CSV row does not affect the others; the remaining placeholders provision normally and only the mismatched device shows as unauthorised.

Blueprint ordering and the conflict trap

Blueprint execution order
  1. Enforce firmware version
  2. Pre-run CLI template   (one-shot; quick install; AUTO-DETACHES)
  3. Provisioning templates (direct assignment OR group-inherited)
  4. Policy package install
Blueprint rule: assign provisioning templates or add the device to a device group — never both on the same blueprint. Directly-assigned and group-inherited templates write into one device database with no defined precedence. That is a conflict, and conflicts have no ordering fix; you remove one author.
Pre-run vs ordinary CLI template: a pre-run template auto-detaches after its quick install, so it runs exactly once. An ordinary CLI template stays assigned and reapplies on every install.

💭 THINK FIRST · AUTHORSHIP

The ownership test decides whether a setting belongs to a template at all. Get it wrong in one direction and you cannot change things fast enough; get it wrong in the other and your change disappears on a Thursday.

  • What test decides whether a setting belongs in a shared template or stays device-local?
  • Not “does the value differ per device” — that is what metadata variables are for. The test is can it survive drift: a setting belongs to a template when it is stable, design-intent-driven, and the template should always win. It stays device-local when it must change faster than a revision-and-install cycle allows.
Q1 — MODEL ANSWER
An install runs. What can it overwrite, and what survives?
Q2 — MODEL ANSWER
An install overwrites every config block an assigned template authors, completely. Anything outside those blocks survives untouched — hostnames, DHCP scopes, local objects. The unit of overwrite is the block, so absence inside an authored block is deletion.

Ownership, blast radius and the countdown

This is the spine of the season and the thread that runs from EP-08 to the finale. Every other mechanism decorates it.

Blast radius is authorship, not device. Anything the template writes is borrowed, not owned. That is why hostnames and DHCP scopes survived Sydney's install and port5 did not.

The season's closing rule

Hand-edit safety
  Hand-edit safety is a property of the device's
  CURRENT ASSIGNMENT SET.

  That set can change without anyone touching the device
  and without anyone intending to change it -- an orchestrator
  re-run regroups and reassigns its own output.

  Therefore: a CLI change to a block a template COULD author
  is not a change. It is a countdown.

ADOM as a boundary

  • ADOM sits above templates as a security and visibility container — not a 1:1 pairing. One ADOM typically holds many SD-WAN templates, one per branch hardware profile.
  • ADOM scope is coarser than site level: an admin scoped to an ADOM sees every device in it. (This is the unresolved contractor-isolation gap from EP-08, formally deferred to Season 5.)
  • The Global ADOM holds shared governance objects — global object database, header/footer policy packages. Not a place for branch templates.

💭 THINK FIRST · VARIATION & SCOPE

Once a setting belongs to a template, three different mechanisms handle the ways devices differ. They are not interchangeable, and the exam tests exactly that.

  • Branches differ in value, in hardware and in build order. Which mechanism handles which?
  • Different value → metadata variable. Different audience → installation target. Different sequence → template group ordering. Template group = who is in the room and in what order they speak; installation target = who is handed this sheet; metadata variable = what is written on the sheet.
Q1 — MODEL ANSWER
An SD-WAN member has an empty Installation Target. Which devices receive it?
Q2 — MODEL ANSWER
All of them. Empty means the absence of a filter, not an empty audience. The field answers “who do I narrow this to” — no answer means no narrowing. Reversed, a new branch would onboard successfully with no SD-WAN members at all.

Metadata variable resolution

Resolution order at install time
  device-level override present?   -> use it
  else template default present?   -> use it
  else                             -> Install Preview BLOCKS that device

  Two independent, layered questions:
    "does this variable have a default"
    "does this device have an override"

  Syntax: $(var) and {{var}} are two syntaxes for ONE store.
  The resolved device config contains no variable syntax at all.
Orphaned mappings — a genuine trap: removing a variable's reference from a template does not delete any device's mapping. The entries become inert, not destroyed, and will resolve again silently if the reference is later reinstated. Deleting a device's own override, by contrast, genuinely destroys data. Different operations, different resurrection risk.

Dependency versus conflict

 DependencyConflict
ShapeOne author needs another's outputTwo authors write the same setting
ExampleCLI template creates port5; SD-WAN template consumes itBlueprint assigning templates and a device group
FixDeclare the sequence (template group)No ordering fix — remove one author
Why order matters at all: the FortiGate is a parser, not a compiler. The assembled install script is consumed line by line and set interface is validated against what exists at that instant. There is no whole-script resolution pass.
Physical vs configuration-created objects: a physical port exists at power-on and cannot be ordered wrong. VLAN subinterfaces, IPsec tunnel interfaces, loopbacks and zones exist only because a command created them — any reference before that command is a reference to nothing.

💭 THINK FIRST · OVERLAY BUILD

The overlay orchestrator looks like a black box and is not one. Everything the season taught about templates explains its output — which is what makes tuning it safe and removing its output from its group unsafe.

  • What must EXIST before you can create an overlay template, as distinct from what you must DECIDE?
  • EXIST: hubs as managed devices with links and interfaces configured; branches in a device group; all devices under one overlay template in the same ADOM; each FortiGate configured by only one overlay template. DECIDE: topology type, overlay address space, loopback address space, BGP AS number. The exam tests these as two different questions.
Q1 — MODEL ANSWER
Why is the hub the dial-up server and the spoke the initiator?
Q2 — MODEL ANSWER
Because of which end knows the other's address. The hub has a static public IP every spoke can be told in advance, so spokes are type static initiators with set remote-gw. Spoke IPs are unknown and mutable, so the hub is a type dynamic dial-up server with one stanza serving any number of spokes. net-device, local ID and mode-cfg all hang off this one fact.
SECTION 06

Building the overlay — orchestrator, IPsec, BGP

The wizard is a template author with ordering built in. It generates IPsec, BGP and CLI templates, adds members and zones to the existing SD-WAN template rather than replacing it, groups its output per device and assigns it. It never touches a firewall — only Install Device Settings does.

Second-order consequence, proved in EP-12: because the orchestrator assigns its own output across the device group, re-running it can newly bind a template to a device that was not the subject of the change. That is exactly how Sydney acquired an SD-WAN template it had never had.

BGP per overlay vs BGP on loopback

Scale comparison — 2 hubs, 4 transports, 30 branches
  TUNNELS are identical under both designs:
    8 overlays per branch, 240 tunnels estate-wide.
    The routing design removes no tunnels.

  BGP SESSIONS differ:
    per overlay    8 per branch    240 hub-side
    on loopback    2 per branch     60 hub-side   (one per hub)

  ROUTES differ too:
    per overlay -- each LAN prefix arrives 8 times, forcing add-path
                   and multiplying reflector cost as routes x peers
    on loopback -- one route per LAN prefix, no add-path required
Exam trap: the scale saving is in sessions and routes, not overlays. Overlay count is set by the IPsec topology and is unchanged by the routing design.

💭 THINK FIRST · FORWARDING

By the end of the season the estate had four tunnels per spoke and two hubs. Explaining what a single packet does across that is the skill Season 3 is built on.

  • Trace a branch packet to a hub-hosted application, naming every route lookup.
  • Ingress → lookup #1 on the inner destination, returning the hub loopback as next hop with no interface → lookup #2 (recursion) on the loopback, resolving through the wizard's static route to the overlay zone → policy lookup → SD-WAN member selection → IPsec encapsulation → lookup #3 on the outer destination, resolving to the physical port the tunnel is bound to → session installed.
Q1 — MODEL ANSWER
Two hubs advertise the same prefix. What decides which one carries the traffic?
Q2 — MODEL ANSWER
Both layers, in sequence. BGP best-path decides how many next hops enter the FIB — by default one. With ibgp-multipath enable, both hub loopbacks are installed, recursion resolves to all four overlays, and SD-WAN's member selection then chooses the hub as a side effect of choosing the tunnel.
SECTION 07

Three lookups — and who decides what

The forwarding decision chain
  LOOKUP #1   inner destination      -> next hop (hub loopback)
              chooses the DESTINATION       BGP-learned

  LOOKUP #2   the loopback           -> overlay zone {members}
              chooses the SET OF PATHS      static, wizard-generated
              [ RECURSION ]

  POLICY      LAN -> overlay zone, accept

  SD-WAN      chooses the ONE PATH   -> overlay1..overlay4
              members are TUNNELS, not physical ports

  ENCAP       outer src from tunnel's bound interface
              outer dst from  set remote-gw

  LOOKUP #3   outer destination      -> default route, physical port
              SD-WAN plays no part -- the tunnel was bound at build time
Why recursion exists: a FortiGate cannot transmit toward an address, only out of an interface. A route naming a next hop with no interface is unfinished, so the next hop is looked up again. Resolution normally completes in one extra step.

Failover, and the layer that owns it

 BGP failoverSD-WAN failover
TriggerSession or route lossSLA breach
Blind toLatency, jitter, packet loss—
GranularityAll traffic, one preferencePer rule, per application

Needs Reinforcement — the season's most dangerous item: without ibgp-multipath enable, only one hub's next hop is in the FIB. The second hub's tunnels are up, green and uncandidate. When the primary dies, the prefix becomes unresolvable and traffic waits for the BGP hold timer to expire before the alternative is even considered. Every dashboard reads healthy throughout.
Needs Reinforcement: a route present in the BGP table but not forwarding is either unresolvable or beaten by a lower administrative distance — usually a leftover static. SD-WAN cannot prevent a route entering the FIB. Route selection into the FIB is the explicit opening topic of Season 3.

The routing table chooses the destination; SD-WAN chooses the transport. Neither can do the other's job, and a design that assumes otherwise installs cleanly and fails silently.

💭 THINK FIRST · FAILURE MODES

Season 2's most valuable output is a catalogue of failures that report success. Every one of them passed an install, showed green, and did something other than intended.

  • Name the two failure timings for a template install and the device state each leaves.
  • Pre-push: an unresolved metadata variable — FortiManager cannot render the script, nothing reaches the device, the install is blocked for that device only, and it is loud. Mid-push: a reference to a not-yet-created object — the FortiGate rejects that one command, everything else lands, the device is partially configured, the job completes with errors and the dashboard shows green. The dangerous failure is the one that does not stop you.
Q1 — MODEL ANSWER
What do the season's quiet failures have in common?
Q2 — MODEL ANSWER
They are all cases where a layer asserts health about something it does not actually measure. A successful install asserts that the script was accepted, not that the intent was achieved. A green tunnel asserts the tunnel is up, not that any route resolves to it. An SLA-met member asserts the path is good, not that it is a candidate.

Order of questions

        Revision history. Look for install jobs the device
        was not the subject of.

  2. WHO authors the affected block right now?
        Assignment history. A template may be new to this device.

  3. What does the DEVICE DB hold versus the RUNNING CONFIG?
        Config Status:  Synchronized / Modified / Out-of-Sync

        There will be no "removing X" line to find.

💭 THINK FIRST · REVIEW & READINESS

Nine questions covering the season. Attempt each before revealing anything; the two below are the pair most likely to be got half-right.

  • You must add a site-specific WAN member to one branch out of thirty. Where does it go, and why not the CLI?
  • Into the shared SD-WAN template as a member with an installation target naming that branch. Not the CLI, because the template authors the whole system.sdwan block — a hand-made member is absent from the template and will be removed by the next install, with no delete instruction and no error.
Q1 — MODEL ANSWER
A device worked on Monday and broke on Friday. Nobody touched it. State the general rule.
Q2 — MODEL ANSWER
Hand-edit safety is a property of the device's current assignment set, and that set can change without anyone touching the device — an orchestrator re-run regroups and reassigns its own output. A CLI change to a block a template could author is a countdown, and Out-of-Sync is the column that tells you it is running.
