Layer 1 · Session 62

Up is a fact. Good is a measurement.

"Up, but not good — that's the lie in the middle,
a road that still works but plays a different fiddle." Your own lyric — Junior wrote it down twice
  • Health check = the measurement. Probes continuously travel each member and report latency, jitter, packet loss for that path.
  • SLA target = the verdict. A pass/fail line drawn across those numbers. One health check can carry several SLA targets; different rules can consume different verdicts.
  • Probes don't follow the routing table. Each probe is stapled to its member — egresses that interface toward the member's configured gateway. That's the only way to measure a road the FIB doesn't prefer.
Thermometer, fever line, other room
The health check is a thermometer. The SLA is the fever line. And a thermometer must be able to touch the patient — J.R. set interface and zone but never typed the gateway, and built a thermometer in another room. Link up all weekend, zero packets.
The dead-member signature: dead  loss 100%  latency 0.000ms — that impossible zero is not "perfect latency." It is no measurement at all. Absence is evidence.
Exam distinction: an SLA breach flips sla(0x1) → sla(0x0) while the member stays alive and the routing table doesn't move. Breach ≠ routing change. A member can be administratively up and still failing its SLA.

Top-down, first match · strategy picks the member
ID > 65535
↓no match → implicit rule
3

The implicit rule = "just use the routing table." Equal-cost members in the zone → ECMP hashing. The Jam lottery.
fallback
  • Both live in one proute table. The ID range is the birth certificate: below 65535 = classic policy route, above = SD-WAN-born.
  • The implicit rule permits nothing and denies nothing — it isn't a firewall decision. It just hands the packet to the FIB.
  • Local-out traffic (the firewall's own — syslog, FortiGuard, DNS) doesn't follow SD-WAN rules by default. The cobbler's children have no shoes — Cipher's syslog was ECMP'd across both links until it was fixed.
Forensic trap: big proute IDs aren't only SD-WAN — ISDB routes land above 65535 too. The tell that an entry is SD-WAN-born is the vwl_service field. Big ID, no vwl_service? ISDB.
Layer 2 · Session 63

"Best" and "acceptable" are different claims

StrategyThe question it asksThe risk
ManualWhich member did you order first (and is it alive)?No quality awareness at all
Best qualityWho is winning right now?Flaps between links every time the lead changes — even with no breach
Lowest cost (SLA)Who is passing the bar? Then: your preference order among themStays on a "worse" link as long as it's acceptable — by design
Load balanceHow do I spread sessions across members?src-all / dst-all / members-1-2 · Friday 16:40 · never again
Why Voice got SLA mode (priority-members 2 1): calls shouldn't chase whichever link is winning by 2ms. Stay on port2 while it passes; move to port1 only when the verdict flips. Stability over the race.
Exam distinction: best-quality is comparative — it can re-steer with no SLA breach at all. SLA mode is threshold — it moves only when pass/fail changes. Distractors swap these constantly.
Layer 3 · Session 64

The gym card: sessions have memory

Front desk vs swipe
🪪 First packet — front desk
  • Full route lookup: proutes → SD-WAN rules → FIB
  • Policy lookup
  • Decision cached into the session: sdwan_service_id, sdwan_mbr_seq, gwy, policy_id
💳 Every later packet — swipe
  • Session-table lookup only
  • The rule is not re-consulted — it isn't even asked
  • Forwarding rides the cached member until the session dies

So when the rule's verdict flips, it flips for the next new session that walks in the door. Existing sessions aren't overruled — they're never re-interviewed. The bouncer changing his mind tonight doesn't revoke cards already in pockets.

🔍
The fingerprint
"New sessions fine, old sessions broken" = session pinning. Every time. First move: look at the session table, not the rule.
Layer 3 · Session 64

Happened vs fired

Reevaluation triggers are routing-table events — member down, route withdrawn, dynamic routing convergence, static route change. When one fires, affected sessions get stamped dirty ("re-check my route on the next packet") and only then does the rule get re-consulted for existing traffic.

Wednesday, replayed — which mechanism touched Jam's call?
09:15 — Baz browns out
Health check watches jitter climb on port2 → sla(0x1) becomes sla(0x0). Member still up, still alive, still in the FIB.
09:16 — Marcus & Aditi redial
New sessions → front desk → rule sees the new verdict → port1. Clean.
09:15 → 10:52 — Jam keeps talking
His session is cached on port2. The dirty machinery never fires — no routing change occurred, so nothing gets stamped. He rides the ocean for 97 minutes, sandwich press in hand.
10:52 — Manual clear
filter → LIST → clear → filter clear. Four-second break, rebuild on port1. Cipher counts the seconds.
The A-distractor: exam options love to narrate the event that happened (the SLA breach) and imply it triggers reevaluation. It doesn't. Only a routing change fires the dirty machinery. Happened ≠ fired.
Clear ≠ dirty: clearing a session is deletion — the next packet builds a brand-new session at the front desk. A dirty stamp is re-evaluation of an existing session after a routing change. Different machinery. Don't let one masquerade as the other.
Layer 3 · Session 64 · Your Hardest-Won Concept

snat-route-change: the mechanism, not the consequence

What the setting actually changes
Default (disabled)
SNAT'd sessions are exempt from the dirty stamp. Routing change fires — they're skipped. They ride the stale path until they expire or you clear them.
→
Enabled: included
SNAT'd sessions get stamped dirty like everyone else when a routing change fires.
→
"Included" = killed
A live NAT'd session can't be renumbered mid-conversation. So it's torn down — the next packet rebuilds fresh, with a new SNAT IP on the new path.

Why the exemption exists: a NAT'd session has committed to a source IP. New egress = new source IP, and the remote end is mid-conversation with the old one. Silently moving it breaks it anyway — so the choice is "let them finish" (default) or "rip the bandaid" (enabled). Escorting dead men to a new door buys nothing.

⚖️
Mechanism sentence — the only accepted answer
Enabled: SNAT sessions are included in the dirty-stamp on a routing change — and because they can't migrate, they are killed so a new session can be born with the new IP. NOT "SNAT just uses the new IP."

Before You Walk In

Exam traps, rapid fire

  • Up ≠ good. A member can be administratively up and failing its SLA. Green dashboards prove nothing about quality.
  • SLA breach ≠ routing change. Breaches steer new sessions; only routing changes stamp existing ones dirty.
  • Happened ≠ fired. The option that narrates the real incident is not automatically the mechanism.
  • Best ≠ acceptable. Best-quality re-steers with no breach; SLA mode moves only on pass/fail.
  • Clear ≠ dirty. Deletion-and-rebuild vs re-evaluation. Different machinery.
  • 0.000ms latency on a dead member is no measurement, not a fast link.
  • Big proute ID ≠ SD-WAN. Check for vwl_service — ISDB lives up there too.
  • Local-out ignores SD-WAN rules by default. The firewall's own traffic is the cobbler's child.
  • snat-route-change enables inclusion-then-termination — never a seamless IP swap.
  • Probes bypass the routing table — stapled to the member's interface + configured gateway. No gateway, no thermometer.
