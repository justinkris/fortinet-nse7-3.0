HA Status, Sync Exceptions & Management Access

The commands that tell you what the cluster is thinking, the settings it refuses to share, and how to reach the member the network can't see.

The one rule underneath everything on this page: cluster identity is shared; member identity is private.
Config sync, vMAC assignment, and reserved management interfaces are all the same rule wearing different hats.
Section 1

HA Verification — the diagnostic order

Status → Uptime → Checksum → Heartbeat → History. Who is primary and why → election standings → are we identical → can we talk → what happened before I arrived.

StageCommandWhat it tells you
Status get system ha status First command, every time. Mode, group name/ID, primary & secondary roles, serials, election reason (“Primary selected using…”), monitored interfaces, sync state.
Status diagnose sys ha status Deeper diagnostic view including heartbeat packet statistics per hbdev.
Uptime diagnose sys ha dump-by vcluster The election scoreboard. uptime/reset_cnt per member — the member showing 0 has the lowest HA uptime; the other value is the gap in seconds. reset_cnt = number of uptime resets.
Uptime diagnose sys ha reset-uptime Run on the primary → zeroes its HA uptime (not system uptime) → graceful failover when override is disabled. No config change.
Checksum diagnose sys ha checksum show Config checksums on the local member.
Checksum diagnose sys ha checksum cluster All members' checksums in one output. Mismatch = out-of-sync cluster.
Checksum diagnose sys ha checksum recalculate Force recalculation when you suspect a stale checksum rather than a real mismatch.
Heartbeat diagnose sniffer packet <hbdev> "ether proto 0x8890" 4 Watch FGCP heartbeat frames directly — “the ballot paper plus pulse.”
Sessions diagnose sys session sync Session-synchronisation statistics between members (matters once session-pickup is on).
History diagnose sys ha history read HA event log: past failovers, role changes, and why they happened.
Access execute ha manage <index> <admin> Jump from primary CLI into the secondary. Checksums and heartbeat counters are per-member — verify on both.
Ethernet-type hook 0x8890 keeps you alive (heartbeat, election, failure detection) · 0x8893 keeps you identical (config sync). Neither is IP — sniff by ether proto, not by address.
Section 2

Config Sync — what rides 0x8893 and what stays home

Shared — synchronised

  • Firewall policies & objects
  • Security profiles
  • Routing, interfaces, VDOMs
  • Users, certificates
  • Essentially everything else in the running config

If it describes what the cluster does for the network, it must be identical on both boxes.

Personal — never synchronised

  • override — per member, CLI only (SG p.88)
  • Device priority — if it synced, it could never break a tie; the feature would delete its own purpose
  • Hostname — so you know which box you're SSH'd into
  • Reserved mgmt interface config + its gateway — its whole job is reaching one specific member
  • Licenses / entitlements — tied to each serial number
  • HA uptime / reset_cnt — runtime state, each member's own
Exam trap Licence mismatch does not block cluster formation — the cluster drops to the lowest licence level among members. “The cluster runs at the level of its poorest member.” What does block formation: different model, firmware, hard-drive config, or operating mode.
Section 3

Reserved Management Interface — reaching the invisible member

Every ordinary interface answers as the cluster — one IP, one vMAC, always the current primary. The secondary is invisible from the network. The reserved management interface punches a deliberate hole: excluded from cluster identity, keeps its real MAC, and each member gives it its own IP and own gateway.

FGT-AFGT-BRule
Reserved portmgmt1mgmt1Same port on both — convention & hygiene, not enforced. Same model → same port names. Different ports = sabotage against the next engineer.
IP address10.99.1.11/2410.99.1.12/24Different IP per member — mandatory; this is the feature's entire purpose. Same subnet is fine.
Gateway10.99.1.110.99.1.1Set per member inside the ha-mgmt config, separate from the routing table — reachability survives being secondary.
Why bother Without it, monitoring (SNMP, syslog source) only ever sees whoever is primary — a dead secondary looks identical to a healthy one. Your only other path to the secondary is execute ha manage: fine for a human, useless for an NMS.
Mental model Same shape, different identity. The port choice mirrors the cluster's symmetry; the unique IP is member identity — the personal-vs-shared rule again, same as vMAC assignment and the sync-exception list.
Section 4

Election Order — the context for every uptime command

Override disabled (default)

  • 1  Connected monitored interfaces (most up wins)
  • 2  HA uptime (highest wins, gap must be ≥ 5 min)
  • 3  Priority (highest wins)
  • 4  Serial number (highest wins)

Graceful failover lever: diagnose sys ha reset-uptime on the primary.

Override enabled (CLI only)

  • 1  Connected monitored interfaces
  • 2  Priority ← jumps above uptime
  • 3  HA uptime
  • 4  Serial number

Graceful failover lever: change a priority. Cost: a second failover (failback) when the preferred primary returns. “Every guarantee has a bill.”
