SUPP-01 · Consolidation · FortiManager

Four Questions Before You Touch a Template

FortiManager isn't a pile of features. It's four dimensions — layer, scope, value, install — and every feature is a point in that space.

Templates aren't places. They're authors. The device database is the page.

Once that lands, CLI templates, SD-WAN templates, device groups, installation targets, metadata variables, Jinja and blueprints all stop competing for the same shelf.

💭 THINK FIRST · THE FRAME

Junior can define every FortiManager noun and relate none of them. That's not a knowledge gap — it's a missing dimension. Before reading on, try to answer his actual question.

  • Once FortiManager manages the Perth branch, how many distinct copies of that device's configuration exist, and where does each one live?
  • Why does FortiManager give you two separate install operations whose status indicators can disagree with each other?
Q1 — MODEL ANSWER
Three. The FortiGate's own running configuration (the only copy carrying traffic); Perth's device database in the device layer (one per managed device); and, in the ADOM policy layer, the policy packages plus one common object database shared across the ADOM.
Q2 — MODEL ANSWER
Cardinality. Device databases are one-to-one with devices; policy packages and objects are one-to-many. Those cannot share a container — you could not edit the shared thing without touching every device referencing it. Two places to make a change means two installs and two statuses.
SECTION 01 · THE ORGANISING IDEA

Four questions, and every feature is an answer

The reason FortiManager feels like an unrelated pile of nouns is that the documentation teaches features, not dimensions. There are only four dimensions. Sort any feature — known or unknown — into them and it stops floating.

QuestionWhat it decidesMechanisms that answer it
1 · Which layer?Where the change is staged, and which install pushes itDevice layer (device DB) · Policy layer (packages + common object DB)
2 · What scope?Which devices receive itTemplate assignment to device/group · Installation targets · Jinja
3 · What value?What goes in the field for this deviceMetadata variables · template default · per-device override
4 · What installs?What the box actually receives, and whether it worksInstall Preview, per device
The central model: a provisioning template is not a storage location. It is an author. It writes into one or more per-device device databases, producing a separate, complete configuration in each. One-to-many at authoring time; one-per-device at storage time.
Analogy

A template is a person writing in notebooks — not a notebook itself.

  • Each managed FortiGate has its own notebook (device database). Nobody shares one.
  • The template is an author who writes the same passage into thirty notebooks at once.
  • If you also write in a notebook by hand, and the author writes over that page — the author wins. Every install. That's why provisioning templates overwrite the device database and take precedence over Device Manager edits.
  • Nothing leaves the notebook until someone posts it. That posting is the install.

SECTION 02 · QUESTION ONE

Which layer am I writing into?

Two layers exist because two kinds of content exist. Per-device content cannot live in a shared container, and shared content cannot live in a per-device container. Everything else follows from that.

Device Layer
One device database per FortiGate
Interfaces · routing · system settings
All provisioning templates
Pre-run CLI templates
Revision history
Install Device Settings
Policy Layer
Packages + ONE common object DB per ADOM
Firewall policies (policy packages)
Addresses · services · security profiles
Normalized interfaces
VPN / AP / FortiSwitch Manager
Install Policy Package

All provisioning templates are device-layer. The type only changes what they author, never where:

TemplateAuthorsStyle
SystemDNS, NTP, admin, SNMP, logging, FortiGuardStructured
SD-WANMembers, zones, health checks, rulesStructured
Static RouteStatic routesStructured
BGPNeighbours, AS, route mapsStructured
IPsec TunnelPhase 1 / Phase 2, tunnel interfacesStructured
CertificateCertificate enrolmentStructured
CLIAnything, as raw FortiGate CLIRaw text
Template GroupA bundle of the above, assigned as one unitContainer
Exam distinction: a CLI template is a kind of provisioning template, not a peer of the SD-WAN template. The real split is structured vs raw. Structured types carry FortiManager's object model — validation, per-model rendering, no syntax risk. CLI templates are shipped largely as text, so correctness is entirely yours.
🧠
MENTAL NOTE
Does it configure the box, or configure traffic decisions? Box → device layer, Install Device Settings. Traffic decisions → policy layer, Install Policy Package.

💭 THINK FIRST · SCOPE

Perth is a 60F with two WAN links. Sydney is a 100F with two WAN links plus a third interface for local breakout. Both should share the same SD-WAN template — identical health checks, identical rules, identical zone structure.

  • What has to be attached to the template for it to write three members into Sydney's device DB and only two into Perth's?
  • Two ways exist to control who gets configuration — assign the template to a device group, or set installation targets inside it. What is the unit being included or excluded in each case?
Q1 — MODEL ANSWER
An installation target, set on the individual member. Not on the device, not on the template — on the member. port5's installation target is Sydney; the other two members leave it empty.
Q2 — MODEL ANSWER
Group assignment switches the whole template on or off for a device — all-or-nothing. An installation target switches one setting inside the template on or off for a device. Coarse filter, then fine filter.
SECTION 03 · QUESTION TWO

Who is this actually going to reach?

Scope has two nested filters, and they operate at different granularity. Confusing them is the main reason template design feels ambiguous.

Scope granularity
Device group assignment  →  WHICH DEVICES get this TEMPLATE     (coarse · template-level)
Installation target      →  WHICH DEVICES get this ONE MEMBER   (fine   · setting-level)

     The group decides who is in the room.
     The installation target decides who is handed which sheet of paper.
Default worth memorising: an empty installation target means the member installs on every device using that template.

But installation targets only exist in structured templates. CLI templates are assigned per device or group, not per line — so they need a different mechanism for structural variation, and that mechanism is Jinja.

MechanismStructured templatesCLI templates
Metadata variable $(x) / {{x}}Yes — in value fieldsYes
Jinja logic {% if %}, loopsNo — no logic layer existsYes
Installation targetYesNo — assignment is per device
Read that table sideways: each template type has exactly one way to vary structure. Structured templates vary structure with installation targets; CLI templates vary structure with Jinja. Same problem, solved the only way each type can. Identify the template type first and the mechanism chooses itself.

Worked example — Sydney's local breakout

The SD-WAN template configures SD-WAN only. It does not give port5 an IP address, an alias or a role. That's a two-template job.

CLI Template — assigned to the whole branch group, Jinja-gated
{% if has_local_breakout == "yes" %}
config system interface
    edit "port5"
        set alias "LOCAL-BREAKOUT"
        set role wan
        set mode static
        set ip {{breakout_ip}} {{breakout_mask}}
        set allowaccess ping
    next
end
{% endif %}
Devicehas_local_breakoutbreakout_ipbreakout_mask
Sydneyyes203.0.113.10255.255.255.0
Perthnounsetunset
Adelaidenounsetunset

Perth's install renders the {% if %} block to nothing. Note the second job Jinja is doing there: it also stops Perth and Adelaide from needing values for variables they have no use for.

The SD-WAN template then consumes the interface — member port5, gateway {{breakout_gw}}, installation target: Sydney. Jinja gates whether the interface is built; the installation target gates whether the member is built.

Ordering risk — verify, don't assume: FortiManager assembles one install script per device. An SD-WAN member referencing port5 is meaningless if the CLI template hasn't created port5 yet. Read the assembled order in Install Preview before the first branch ships, and adjust template group ordering if the member lands above the interface.
🧠
MENTAL NOTE
Structured template → vary structure with installation targets. CLI template → vary structure with Jinja. Never the other way round; the other way round doesn't exist.

SECTION 04 · QUESTION THREE

Where does the value come from?

Same template, same member, both devices need it — but the content of the field differs. That's a metadata variable, and it resolves at write time, not at run time.

Resolution pipeline
Template  ── holds the variable reference:  set gateway {{gateway}}
    │
    │   resolve, in strict order:
    │       1. device-level override   (per-device variable mapping table)
    │       2. template default
    │       3. BLOCK — Install Preview stops THIS DEVICE only
    ▼
Device DB ── holds the literal:          set gateway 203.0.113.1
    │
    │   Install Device Settings
    ▼
FortiGate ── holds the literal. Has no concept of variables at all.
Syntax, not two features: $(gateway) is the original metadata-variable syntax; {{gateway}} is the Jinja form added when CLI templates gained Jinja support. Same variable store, same lookup. Use the Jinja form in Jinja-mode templates; either works in a plain CLI template.
⚠ NEEDS REINFORCEMENT — two passes, same error. Deleting a device override and deleting a template reference are not the same operation, and only one of them causes default fallback.
OperationEffect on device dataEffect on resolution
Delete the device's overrideDestroys the value permanentlyFalls back to template default; blocks if none exists
Delete the template's referenceNothing — the value survives, inertNo lookup occurs at all. Not the default. Nothing.

The sting on row two: reinstate a reference to that variable name in any template six months later and the old, stale value resolves again silently, with no warning that it was ever orphaned.

🧠
MENTAL NOTE
Default fallback only happens while a reference still exists. No reference, no lookup — and the device's value is still sitting there waiting to resurrect.

SECTION 05 · QUESTION FOUR

What will Install Preview actually show?

Nothing in FortiManager reaches a FortiGate until an install runs. Editing only ever changes a staged copy — which is exactly what Modified status is reporting.

Assign is not install
Assign    →  link created between template and device/group
             device status goes MODIFIED
             NOTHING is written to the FortiGate

Install   →  template renders into the device DB
             device DB is pushed to the FortiGate

Unassign  →  link removed
             device DB KEEPS whatever was already written
Exception: a pre-run CLI template is assigned, quick-installed, and auto-detached — all handled for you. That's the difference from an ordinary CLI template, which stays assigned and reapplies on every subsequent install.

Failure is per device, not per run

A CLI template containing set interface port5, assigned to a group holding Perth (60F, no port5) and Sydney (100F, has port5):

DeviceOutcomeWhy
SydneyInstalls normallyport5 exists on a 100F
PerthFails — this device onlyThe command is rejected; nothing rolls back for anyone else
The structured/CLI difference under failure: with a structured template FortiManager understands the object model — it knows a member points at an interface and can tell that interface isn't in Perth's device DB. With a CLI template it is largely shipping text; there is no validator watching your CLI for you. Install Preview is where you see it.
Same principle, three triggers: unresolved variable · nonexistent interface reference · invalid CLI for the platform. All three block the affected device only, all three are visible in Install Preview before anything is pushed.

One more install fact worth carrying: installation is reference-driven, not inventory-driven. A policy package install carries the policy and the objects that policy references. Objects sitting in the ADOM common object database that nothing in the package references are not pushed at all — they stay in the ADOM.

🧠
MENTAL NOTE
Install Preview is the only place you see what a specific box is about to receive — assembled, in order, with every variable already resolved.

SECTION 06 · ONBOARDING

Device blueprints — the one-off recipe

A device blueprint is a recipe applied automatically when a new FortiGate first calls home. Instead of receiving an unauthorised device and configuring it, FortiManager matches the incoming device to a blueprint and authorises plus builds it unattended.

Device Manager > Device & Groups > Device Blueprint

SettingEffect
Automatically Link to Real DeviceBinds the model device to the real one on arrival — required for ZTP/LTP
Enforce Firmware VersionUpgrades or downgrades before any config is applied
Enforce Device ConfigurationLets FMG reconfigure the interface the FortiGate uses to reach it — misconfiguration breaks the FGFM connection and fails the whole ZTP process
Pre-Run CLI TemplateRuns before other provisioning templates; auto-detaches afterwards
Assign Policy PackageWhich package the device receives
Provisioning TemplatesTemplates or template groups assigned directly
Device GroupGroup membership — device inherits the group's templates
Blueprint order of operations
1.  Enforce Firmware Version        firmware first, before any config
2.  Pre-Run CLI Template            one-shot, then auto-detaches
3.  Provisioning templates          direct OR group-inherited
4.  Policy package install

    NOT guaranteed: ordering BETWEEN provisioning templates at step 3.
    → that's what template group ordering and Install Preview are for.
Documented trap: on the same blueprint, assign provisioning templates OR add the device to a group — not both. Directly-assigned and group-inherited templates write into the same device database with no defined precedence. Whichever writes last wins, and you cannot predict it from the GUI. Two authors, one page, no referee.
Blueprints are one-off. They fire on first contact and then play no further part. Group membership, template assignments and the policy package persist; the blueprint does not re-run. Editing a blueprint later does not affect devices already onboarded.

Paired with a CSV of serial numbers, blueprints are how thirty branches get built without thirty build sessions — each row carries the serial number, the blueprint, the device name, and the metadata variable values for that site.

🧠
MENTAL NOTE
Blueprint = onboarding recipe, fires once. Firmware, then pre-run CLI, then templates, then policy. Templates OR group — never both.

SECTION 07 · REVISION

Traps, distinctions, and the four questions again

TrapThe correction
"The policy package lives in the device database"Policy layer, one shared object DB per ADOM. Per-device and shared content cannot share a container.
"A template is where the config lives"A template is an author. Config lives in the per-device device database.
"CLI template and SD-WAN template are different things"Both are provisioning templates. The split is structured vs raw.
"Jinja gives me conditional logic in any template"CLI templates only. Structured templates have no logic layer — they use installation targets.
"$(var) and {{var}} are two features"Two syntaxes, one variable store, one lookup.
"Deleting the template reference falls back to the default"No reference means no lookup at all. The device's override survives, inert, and resurrects silently later.
"Assigning a template pushes it"Assign creates a link and marks Modified. Install writes.
"One device's bad config fails the install run"Install validation and failure are per device.
"Install Device Settings will deliver my new policy"Wrong layer. A policy package install alone carries the policy and its referenced objects.
"Empty installation target means nobody"Empty means everybody using that template.

Before you touch a template

The four questions
1.  Which layer am I writing into?
        → determines which install pushes it

2.  Who is this going to reach?
        → group assignment (template-level)
        → installation target (setting-level, structured only)
        → Jinja (CLI only)

3.  Where does each value come from?
        → override, then default, then block

4.  What will Install Preview show for the WORST device in the group?
        → the one with the least hardware, the fewest variables set
Senior engineering lesson: when a product feels like a pile of unrelated features, the thing you're missing is usually not a definition — it's a dimension. Find the dimensions and the fifteenth feature becomes trivial to learn.

MENTAL NOTE
Layer decides what install pushes it. Scope decides who receives it. Variables decide what's in it. Install Preview shows the result.
