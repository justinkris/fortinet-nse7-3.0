EPISODE 02 · SD-WAN HEALTH & SLA

Up Is Not Good

A member can answer every probe and still be useless — alive and compliant are two different questions, answered from the same measurement.

The dashboard said green. Priya said the calls were breaking up. Both were telling the truth.

This episode is about learning to distrust a status word the moment it stops matching the experience it's supposed to describe — and knowing exactly which command proves you right.

💭 THINK FIRST · ALIVE VS GOOD

The SD-WAN dashboard shows both Tuggers WAN members as "Alive." Priya is reporting Teams stutter and licensing timeouts. Before looking at any numbers — what is "Alive" actually verifying, and what has it never claimed to verify?

  • What single question does a health check probe answer when it marks a member Alive?
  • Does answering that question require, or say anything about, latency, jitter, or packet loss?
Q1 — MODEL ANSWER
Alive answers exactly one question: did the probe return before the configured timeout? It is a pure reachability fact.
Q2 — MODEL ANSWER
No. Reachability says nothing about quality. A member can return every probe on time while carrying 300ms+ latency, heavy jitter, and packet loss — Alive is blind to all three.
SECTION 01

Alive Is a Fact. Good Is a Measurement.

"Alive" and "Good" answer two completely different questions, and FortiOS never conflates them internally — it's the dashboard's single green dot that tempts an administrator to conflate them. Alive is derived purely from probe success/failure against a timeout. Good is a compliance verdict: are the values this same health check is already measuring within the SLA targets you configured?

The critical insight from this episode is that the health check is a continuous instrument, not a simple ping. Every probe round-trip — with zero extra tooling and before any SLA target is even configured — already yields three raw measurements:

  • Latency — the round-trip time of the probe itself.
  • Jitter — the variance in round-trip time between successive probes.
  • Packet loss — whether probes come back at all.
Analogy

Health check = thermometer. SLA target = fever line.

  • The thermometer is always measuring — that's the raw latency/jitter/loss data.
  • The fever line is a threshold laid over the same reading — that's the SLA target.
  • "Alive" only asks whether the thermometer is still attached to the patient — not what it reads.
Common misconception: Assuming a "green" or "Alive" member is fine for latency-sensitive traffic. A member can pass every probe and still be carrying 342ms latency and 4% packet loss — exactly what happened to Tuggers' port1 this episode.
🧠
MENTAL NOTE
Alive = probe returned in time. Good = the same measurement compared against a configured threshold. Never trust one to imply the other.

💭 THINK FIRST · SLA_MAP & STRATEGY

sla_map looks like a simple bitmask, and it is — but it's easy to misread what each bit represents. Getting this wrong under exam pressure is a classic trap.

  • In a health check with three configured SLA targets, does each bit in sla_map represent a different member, or a different target on the same member?
  • Under a Lowest Cost (SLA) rule, if a member fails just one of its three targets, is it deprioritized or fully excluded from candidate selection?
Q1 — MODEL ANSWER
Each bit is one configured SLA target within a single member's health check (e.g. bit0=latency, bit1=jitter, bit2=packet loss), read LSB-first. It is not one bit per member.
Q2 — MODEL ANSWER
Fully excluded. Lowest Cost (SLA) first filters to members passing ALL configured targets, then picks the cheapest survivor. Failing even one target removes the member from consideration entirely — cost is never even compared for it.
SECTION 02

Reading the Bitmask, Trusting the Filter

sla_map is a per-target bitmask for one member's health check — not a bit per member. Bit 0 (least significant bit) corresponds to the first configured SLA target, bit 1 to the second, and so on. A 1 means that target is currently passing; a 0 means it's failing.

sla_mapBinaryTarget 1 (latency)Target 2 (jitter)Target 3 (loss)
0x7111PASSPASSPASS
0x5101PASSFAILPASS
0x0000FAILFAILFAIL
Exam trapNeeds Reinforcement: It's tempting to read sla_map bits as "member 1, member 2, member 3." They are not — they are targets within one member's health check. This confusion cost a wrong exam answer this session before being corrected.

This is why the strategy matters as much as the measurement. Lowest Cost (SLA) is a two-stage filter: first eliminate any member failing even one configured SLA target, then compare cost only among the survivors. It does not rank or deprioritize a partially-failing member — it removes it from consideration entirely.

StrategyConsults sla_map?Selection logic
ManualNoFirst member in configured preference order that is Alive — SLA status irrelevant.
Lowest Cost (SLA)YesExclude any member failing any target, then pick cheapest among survivors.
Best QualityYes (continuously)Pick whichever eligible member is currently winning on the chosen quality metric.
🧠
MENTAL NOTE
sla_map = one bitmask per member, one bit per configured target. Lowest Cost SLA excludes on any single target failure — it never merely deprioritizes.

💭 THINK FIRST · TROUBLESHOOTING

The rule turns out to be correct, and port2 is clean. Yet Priya's stutter continues. If the rule is already steering new sessions away from the sick link — what's left to blame?

  • What single command shows real latency/jitter/loss values alongside sla_map, so you can prove degradation instead of inferring it?
  • If the rule is provably correct, what category of traffic is not the rule's responsibility at all?
Q1 — MODEL ANSWER
diagnose sys sdwan health-check status <name> — prints per-member latency, jitter, packet loss, and sla_map together.
Q2 — MODEL ANSWER
Existing/established sessions. The SD-WAN rule only chooses a path for a session at creation — it does not re-run that choice for sessions already forwarding on an interface.
SECTION 03

Evidence Before Theory, Rule Before Session

The workflow this episode modeled: don't accept a status word, and don't accept a bitmask verdict either — pull the raw numbers that produced it.

FortiOS CLI
diagnose sys sdwan health-check status office_sla

Member: port1 (SD-WAN wan1-zone)
  Latency: 342.5ms, Jitter: 61.2ms, Packet Loss: 4.0%
  sla_map=0x0   (all 3 targets FAIL)

Member: port2 (SD-WAN wan1-zone)
  Latency: 28.1ms, Jitter: 6.4ms, Packet Loss: 0.1%
  sla_map=0x7   (all 3 targets PASS)

Those raw numbers separate two very different diagnoses that would otherwise look identical from sla_map alone:

Scenariosla_map resultDistinguishing evidence
Link genuinely degraded0x0 (all fail)Measured values wildly outside any reasonable threshold (342ms latency)
Threshold set too tight0x0 (all fail)Measured values close to threshold (e.g. 32ms latency vs a 30ms target)
Key move: sla_map alone cannot tell these two scenarios apart — it's a verdict, not evidence. The raw latency/jitter/loss numbers sitting right next to it are what settle the question.

With port1 confirmed genuinely sick, and port2 confirmed clean, the Lowest Cost SLA rule should already be avoiding port1 for new sessions. That apparent contradiction — a correct rule, a persistent symptom — is itself the clue: the affected calls must be existing sessions that started before port1 failed SLA, and which never get re-evaluated against the rule after being pinned to an interface.

FortiOS CLI
diagnose sys session filter dst <teams-server-range>
diagnose sys session list

This two-step filter-then-list workflow narrows the session table to just the relevant sessions and reveals which outgoing interface each is actually bound to — proof, not inference, that stuck sessions are riding the degraded link.

🧠
MENTAL NOTE
A correctly steering rule only governs new sessions. If the rule is provably right and the symptom persists, look at the session table, not the rule.

SECTION 04

Recap, Topology, and Exam Traps

Business outcome: Priya's stutter and licensing timeouts were never a rule failure. Port1 degraded severely while remaining Alive; the Lowest Cost SLA rule correctly steered new Teams sessions to port2. The residual pain was existing sessions pinned to port1 before it failed SLA — a session-state problem, not a rule problem.

Telstra Tower→Tuggers HA Cluster
wan1-zone port1 · 500Mb · sla_map=0x0 (degraded) port2 · 200Mb · sla_map=0x7 (healthy)
SD-WAN Rule→Teams (ISDB) · Lowest Cost SLA · confirmed correct

No topology change this episode — the existing EP-01 design was validated, not modified.

Senior engineering lesson: Never trust a status word as a substitute for the measurement behind it. When behavior contradicts the dashboard, go to the raw numbers next to the verdict — the verdict can lag reality; the measurement can't.
  • Alive ≠ Good — reachability vs SLA compliance are separate questions from the same data.
  • sla_map is per-target, per-member, LSB-first — not per-member Needs Reinforcement.
  • Lowest Cost SLA excludes on any single target failure — it does not deprioritize.
  • Manual strategy ignores sla_map entirely — Alive-only preference order.
  • Rule correctness ≠ symptom resolution — established sessions are not re-evaluated against SD-WAN rules.
