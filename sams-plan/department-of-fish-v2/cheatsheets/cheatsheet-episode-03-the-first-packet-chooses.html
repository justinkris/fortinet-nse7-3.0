The First Packet Chooses

A rule only ever gets asked once. Everything after that is memory, not measurement.

Priya's incident closed itself out — not because anything was fixed, but because every affected session eventually ended. That's the clue.

EP-02 proved the SD-WAN rule was steering new sessions correctly the whole time. EP-03 explains why a correct rule and a lingering symptom can coexist — and what actually has to change for an existing session to move.

Two Planes Re-eval Triggers Refresh vs Rebuild Strategy Contrast
💭 THINK FIRST · TWO PLANES

Before reading the model — a Teams call has been running for twenty minutes on port1. Somewhere in that time, port1's SLA measurements go bad, but the interface never actually goes down.

  • How many times does FortiGate consult the SD-WAN rule table over that call's entire lifetime?
  • Does a changing SLA verdict, on its own, ever reach into an already-established session?
Q1 — MODEL ANSWER
Once — at the moment the very first packet of the session arrives. The rule table is never consulted again for that session's lifetime.
Q2 — MODEL ANSWER
No. The SLA verdict lives entirely on the inspection plane. An established session's forwarding is governed by the forwarding plane only, and nothing notifies it when sla_map changes.

The front desk is consulted once; the hallway runs on memory alone.

Every new session's first packet triggers exactly one SD-WAN rule lookup. That lookup reads the inspection plane — the live health-check measurements (latency, jitter, packet loss, sla_map) — and picks a member. The result of that single decision gets written into the session as its forwarding plane entry: a cached interface and next-hop.

Every packet after the first uses that cached entry directly. There is no polling loop walking the session table asking "is your member still SLA-compliant?" The two planes are structurally separate, and only one of them ever touches a session that already exists.

Remember: Inspection plane = measured continuously, but only read at session birth. Forwarding plane = written once at session birth, then reused for every subsequent packet with zero re-lookup.
🧠
MENTAL NOTE
First packet visits the front desk and gets an access card. Every later packet just shows the card — the desk is never revisited.
SECTION 02

What Actually Tears Up the Card

Only two events force an established session's next packet back through the rule engine — and an SLA verdict, however severe, is not one of them.

EventPlaneForces re-evaluation?
Health check fails one or more SLA targets (sla_map worsens)InspectionNo — new sessions only
Member goes physically/fully down (FIB withdraws the route)ForwardingYes
Routing protocol neighbour lost (e.g. BGP down), route withdrawnForwardingYes
Administrator or script manually clears the sessionSession table (direct)Yes
SD-WAN rule cost value edited in the GUIInspection / configNo — new sessions only
Exam trap: Both "sla_map degrades" and "rule cost is edited" sound like they should matter to a live session — they don't. Neither touches the cached FIB entry an established session is forwarding against.

This is exactly why EP-02's incident resolved itself with time rather than configuration: port1 never left the FIB. It stayed the correct, reachable next-hop the entire time — only its SLA compliance changed. Existing Teams sessions had no trigger to act on.

🧠
MENTAL NOTE
Rule correctness ≠ session correctness. A rule can be steering new sessions perfectly while old sessions ride out a degraded path indefinitely — until the FIB itself changes.
SECTION 03

Proving Refresh vs Rebuild

When a genuine FIB/route change does occur, the existing session's cached forwarding info is typically refreshed in place — same 5-tuple, same session identity, only the interface and next-hop fields get updated. It is not, in the simple case, torn down and recreated from scratch.

Deferred, not forgotten: SNAT-translated sessions can behave differently — sometimes killed and rebuilt rather than refreshed. That distinction is covered properly in a later episode on SNAT and route changes. Park it for now.

The trap is picking the wrong evidence to prove which one happened. The SD-WAN member/interface field in the session entry will show the new interface either way — refreshed or rebuilt — so it can never prove which occurred.

FortiOS CLI
diagnose sys sdwan health-check status <health-check-name>
  → per-member latency / jitter / packet-loss and sla_map (inspection plane)

diagnose sys session list
  → filter to the flow's 5-tuple; check the session's duration/age counter
EvidenceValid proof of refresh vs rebuild?
SD-WAN member/interface field changedNo — changes under both scenarios
sla_map value changedNo — inspection-plane only, unrelated to session identity
Session duration/age counter is continuous (not reset)Yes — proves the same session survived
New session entry appears, age near zero, old entry goneYes — proves the session was torn down and rebuilt
🧠
MENTAL NOTE
The session's own clock is the proof. Fields that describe where traffic goes now can't tell you whether it's the same session — only the age counter can.
SECTION 04

Manual vs Lowest Cost SLA — Same Member, Different Outcome

Same physical scenario: the top-priority member is degraded but still Alive. Two different strategies, two different outcomes for a brand-new session — because the strategies read different data.

StrategyReads sla_map?New session assigned to degraded-but-Alive top member?
ManualNo — SLA-blind by designYes — walks preference order, picks first Alive member
Lowest Cost (SLA)Yes — SLA-gated by designNo — demoted below any passing member
Needs Reinforcement

Refinement to the EP-02 model: Lowest Cost SLA does not remove an out-of-SLA member from candidacy — it demotes it to the bottom of the same cost-ordered outgoing interface list. Cost remains the primary discriminator throughout; configuration order only breaks a tie when costs are equal — even among the demoted, failing members.

This is indistinguishable from "hard exclusion" whenever at least one member is passing SLA. It only diverges in the edge case where every member fails SLA: the rule does not refuse to assign an interface. It still selects the cheapest-cost member among the failing set.

Common mistake: Assuming the all-fail case switches to a totally different selection method (e.g. configuration order first). It doesn't — cost stays primary; the list simply ran out of passing candidates before you reached the bottom.
Needs Reinforcement

Retention under pressure: in a direct exam-style question, "FortiGate periodically re-checks active sessions against SLA compliance" was briefly marked True before self-correcting to False on request. The model itself is solid — this is a flag to retest the same idea cold, in a fresh scenario, before the real exam.

🧠
MENTAL NOTE
Lowest Cost SLA is a re-ordering of a cost list, not a removal from one. When nothing passes, the cheapest failure still wins.
EXAM DISTINCTIONS

Key Takeaways

  • Rule lookup happens once, at session birth — never again for that session's life.
  • Only two real triggers re-evaluate an existing session: a manual/admin clear, or a genuine FIB/route change. An SLA verdict alone is never one of them.
  • The session's duration counter is the only valid evidence for "refreshed in place" vs "torn down and rebuilt" — the SD-WAN member field changes either way and proves nothing.
  • Manual strategy is SLA-blind; Lowest Cost SLA is SLA-gated — identical member health can produce different new-session outcomes purely based on strategy choice.
  • Lowest Cost SLA demotes, it doesn't delete — when every member fails SLA, the rule still picks the cheapest-cost failure rather than refusing to route.
Topology this episode: No configuration or physical changes. Tuggers HA cluster, wan1-zone (port1 500Mb / port2 200Mb), one explicit Teams/ISDB rule on Lowest Cost SLA — unchanged from EP-01/EP-02. This was a pure mental-model and diagnostic-evidence episode.
