EPISODE CONTEXT

The Business Problem

Story: Telstra Tower executive floor reports inconsistent video-conferencing quality — calls stutter for some staff while file downloads run fine, and the affected users change day to day. Priya Nair escalates it as "the network is random."

Technical trigger: The Tuggers FortiGate HA cluster has two WAN members in a zone, with health checks already running — but the SD-WAN rule table is completely empty. Every new session falls to the implicit rule.

Root cause: The implicit rule load-balances new sessions by a source-IP hash. That hash is blind to both link capacity (500 Mb vs 200 Mb) and link quality (the SLA data the health check is already collecting). Users get pinned to a member for the whole day — hence "random," not actually random.

SECTION 02

New-Session Decision Order

When a brand-new session arrives, FortiGate evaluates in this order:

  1. Explicit SD-WAN rules — evaluated top-down, first match wins (same logic as firewall policy lookup).
  2. Implicit rule (if no explicit match) — default source-IP hash, load-balances across zone members using FIB knowledge, but blind to capacity and SLA.
Exam tip: The implicit rule is not a failure state — it's a designed fallback. But "unmatched" traffic still gets spread across members with zero awareness of link quality or bandwidth.
SECTION 03

Decoding the sla_map Bitmask

⚠ Needs Reinforcement

Output of diagnose sys sdwan health-check status. The sla_map field is a hexadecimal representation of a binary bitmask, one bit per configured SLA target.

  • Bit 0 (rightmost) = 1st configured SLA target
  • Bit 1 = 2nd configured SLA target
  • Bit 2 = 3rd configured SLA target, and so on
  • 1 = target met · 0 = target missed
sla_map (hex)BinaryDecoded (targets 1→4)
0x20010T1 missed · T2 met
0x50101T1 met · T2 missed · T3 met
0xB1011T1 met · T2 met · T3 missed · T4 met
Common trap: Reading the bitmask left-to-right instead of from bit 0 (rightmost), or mis-converting the hex digit to binary. Always write out the full binary string digit-by-digit before mapping bits to targets.

SECTION 05

Troubleshooting Workflow Used

  1. Symptom: inconsistent video quality, affected users change daily.
  2. Hypothesis 1: link saturation from concurrent downloads.
  3. Evidence: config review — 500Mb + 200Mb members, health check active, rule table empty.
  4. Refine hypothesis: implicit rule hash ignores both capacity asymmetry and SLA/quality data.
  5. Root cause confirmed: no explicit rule exists to consume the SLA measurements already being collected.
  6. Design fix: explicit rule — ISDB match on Teams, Lowest Cost (SLA) steering strategy.

SECTION 07

Exam Distinctions & Traps

Health check vs SLA target: the health check is the ongoing measurement; the SLA target is the pass/fail threshold applied to it. A member can be alive and still miss its SLA.
"Up" vs "good": a member can answer every probe (alive) while being useless for voice/licensing traffic (fails SLA). This is next episode's core distinction — keep it sharp.
Throughput ≠ quality: a throughput threshold tells you a link is busy, not that latency/jitter/loss are acceptable. Steering strategies for real-time traffic should consume SLA data directly (Lowest Cost/SLA), not a bandwidth proxy.
ISDB vs Application Control: ISDB matches from the first packet (pre-known IP ranges for known services like Teams). Application Control needs several packets of deep inspection before it classifies traffic — it always steers a little late.
