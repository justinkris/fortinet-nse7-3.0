Episode 14 · Department of Fish · NSE 7 SNA

OSPF Over IPsec

A tunnel that answers hellos is not a tunnel that works. Routing proves reachability; only SD-WAN judges quality.

Fisheries arrives with its own OSPF domain — and two paths to us that nothing can measure.

Equal cost puts two hubs in the FIB. A hash picks between them. Neither OSPF nor BFD can tell you one of them is quietly rotting.

Story & Problem Adjacency ECMP Failure Boundary Exam & Traps
💭 THINK FIRST · STORY & PROBLEM

A machinery-of-government transfer hands the Department eleven Fisheries sites running their own OSPF area 0. They must reach Department resources. The temptation is to join the two networks everywhere they touch. The cost of that decision is paid during incidents, not during the build.

  • Why terminate the Fisheries OSPF domain at two hubs rather than at every branch that could reach it?
  • Darwin's static was correct the day it was typed. Which part of the Fisheries design has the same property?
Q1 — MODEL ANSWER
Every redistribution point is a place routing policy is authored. Two borders means two places to look during an incident and two places policy can drift; eleven means eleven. Branches stay iBGP-only, never hold a prefix two ways, and therefore have no AD contest at all.
Q2 — MODEL ANSWER
The prefix-list. It enumerates a state — actual subnets on a given day — rather than expressing a rule. When Fisheries adds a site, it is silently wrong and the symptom is an absence, not an alarm. Prefer policy that expresses a rule; where you must enumerate, give it an owner and a review trigger.
SECTION 01

The Situation and the Business Problem

Cold open — Darwin closed out. The Rev 27 static to 10.60.20.0/24 via the ISP1 gateway was removed by CLI template. It was hand-typed in April, before Darwin had tunnels, and at AD 10 it had beaten the iBGP overlay route (AD 200) ever since. Compliance traffic left port1 in the clear, addressed to RFC1918 space, and was discarded at the ISP.

Why it survived four months: a static route stays in the FIB while its next hop is reachable. It is never validated against the destination. The ISP gateway was directly connected and perfectly healthy, so FortiOS was content. Link monitors and SLA checks exist to supply the missing test; this static had neither.

The new problem. The Fisheries Compliance Division transfers on 1 September: eleven sites, its own routers, an existing OSPF area 0. Dr Finch must sign that compliance data goes where the Department says it goes. The design decision from EP-13 stands — Fisheries meets the Department overlay at Tuggers and Gunners only.

Fisheries is not a Department branch. It is a separate network that already exists, joined at two controlled borders. Department branches never form an OSPF adjacency and never learn that OSPF exists — they receive Fisheries prefixes over the iBGP they already run.

💭 THINK FIRST · ADJACENCY

Two FortiGates, a tunnel between them, OSPF enabled on both. That is not yet enough. Our iBGP overlays have never needed the thing OSPF now requires — and the reason is in how each protocol finds its peer.

  • What must exist on the tunnel interfaces before an OSPF adjacency can form, and why does BGP not need it?
  • Twelve dial-up spokes, all tunnels up, no adjacency reaches Full. What single setting explains it?
Q1 — MODEL ANSWER
IP addresses on both tunnel interfaces, in the same subnet with the same mask. OSPF hellos are multicast to 224.0.0.5 and are link-local — they are never routed. BGP dials a unicast TCP session to an address you configure and only needs a route to reach it.
Q2 — MODEL ANSWER
Network type. With net-device disable every dial-up tunnel lands on one IPsec virtual interface, so the point-to-point default is false. Set the hub to point-to-multipoint. Type must match at both ends, and the timers differ (30/120 vs 10/40), so a mismatch never reaches Full.
SECTION 02

Forming an Adjacency Across a Tunnel

OSPF needs a room; BGP dials a number. That single distinction explains the addressing requirement.

iBGPOSPF
TransportTCP 179, unicastIP protocol 89, multicast 224.0.0.5
Peer identityAn address you type — can be a loopback several hops awayWhoever answers on this link
Needs link addressing?No — needs a route to the peerYes — hellos are link-local, never routed

Three things must all be true, and none of them is automatic:

  • Tunnel interfaces addressed at both ends, same subnet, same mask. A /32 with a mismatched remote-ip prefix will pass traffic happily and silently never peer.
  • OSPF enabled on the tunnel interface under config ospf-interface.
  • The tunnel subnet covered by the OSPF network statement.
Adjacency requirements (all must match): primary IPs in the same subnet with the same mask · same interface type and same area · matching hello and dead intervals · unique router IDs · matching OSPF IP MTU · successful authentication if enabled.

Network Types — the mechanics

Point-to-pointBroadcastPoint-to-multipoint
Neighbours on interfaceExactly 1ManyMany
Medium supports multicast?n/aYesNo
DR / BDR elected?NoYesNo
Hello / Dead10 / 4010 / 4030 / 120
Link advertised asSubnetSubnet/32 host route per neighbour
Typical useSingle site-to-site tunnelEthernet LANDial-up hub, NBMA
  • Point-to-point — two routers, one wire. No election, no ambiguity, adjacency forms immediately. FortiOS default on tunnel interfaces.
  • Broadcast — many routers on a medium that can multicast. DR/BDR exist purely for adjacency reduction: ten routers would otherwise form 45 adjacencies.
  • Point-to-multipoint — many routers on one interface that cannot multicast to each other. Treated as a bundle of separate point-to-point relationships. No DR, because there is no medium to elect one on.
FortiOS CLI — dial-up hub
config router ospf
    config ospf-interface
        edit "Hub-Fisheries"
            set interface "VPN1"
            set network-type point-to-multipoint
        next
    end
end
Exam trap: point-to-multipoint's default timers are 30 / 120, not 10 / 40. Setting the network type on the hub changes your convergence budget without you touching a timer.
🧠
MENTAL NOTE
net-device disable collapses many tunnels onto one interface — so point-to-point becomes a lie, and the hub must be point-to-multipoint.

💭 THINK FIRST · ECMP

Fisheries has an adjacency to each hub and has expressed no preference. For both hubs to end up in the FIB, several things must be equal — and "the cost is the same" is not the whole list, because Department prefixes arrive in OSPF as externals.

  • What has to be equal before two hubs install as separate next hops?
  • Two next hops are installed. Which one carries a given session, and what decides?
Q1 — MODEL ANSWER
AD is equal by definition (110 vs 110), so the contest drops to metric: equal total path cost, with auto-cost reference-bandwidth consistent across the domain. Because these are Type-5 externals from two ASBRs, also the same metric type from both — and rfc1583-compatible enable, since by default FortiGate does not load balance external routes.
Q2 — MODEL ANSWER
A deterministic hash, computed once at session birth and cached in the session table. Default v4-ecmp-mode is source-ip-based — source IP only. Equal cost spreads load only if the sources are spread.
SECTION 03

Equal Cost Is Not Load Balancing

Both paths are OSPF, so there is no administrative-distance contest — 110 against 110. The comparison drops straight to metric, which in OSPF is the cumulative cost of the whole path, not one link. auto-cost reference-bandwidth derives each interface cost and must be identical on every router in the domain, or two engineers compute different costs for the same topology and neither knows.

The part the question hides: Department prefixes do not originate in OSPF. They are redistributed into OSPF at both hubs, so Fisheries sees them as Type-5 externals from two different ASBRs — and by default FortiGate does not load balance external OSPF routes.
Metric typeCost seen by receiverConsequence
E2 (default)Seed metric only — internal cost to the ASBR is not addedBoth hubs advertise the same cost however far away they are. Ties are broken by forwarding cost to the ASBR / RFC 2328 preference rules.
E1Seed metric + accumulated internal costTunnel cost genuinely influences the choice. Destroys the equal-cost tie.
FortiOS CLI
config router ospf
    set rfc1583-compatible enable          <-- selection based solely on cost
    config redistribute "bgp"
        set status enable
        set metric 20
        set metric-type 2                  <-- default; 1 = E1
    end
end

config system settings
    set v4-ecmp-mode source-ip-based       <-- default
end
v4-ecmp-modeHashes onConsequence
source-ip-based (default)Source IP onlyOne host always takes the same next hop, for every session, to every destination
source-dest-ip-basedSource + destinationA host's sessions spread by destination
weight-basedConfigured interface weightDeliberate ratio rather than a hash
usage-basedCurrent interface bandwidthAdaptive
Same shape, different layer: v4-ecmp-mode is a system-wide routing setting for equal-cost FIB entries. SD-WAN's load-balance-mode is an SD-WAN setting for members under the implicit rule. Both hash at session birth; neither is SLA-aware.
No mode splits a single session. A 300 GB nightly backup from one source will pin to one path under every mode — splitting a TCP flow would reorder packets. A hash problem is not solved by changing the hash; it is solved by removing the flow from the hash (schedule it, shape it, or steer it with an SD-WAN rule). Do not fix it by making the tunnel costs unequal — that destroys the second FIB next hop and with it SD-WAN's second eligible member.
🧠
MENTAL NOTE
Two equal-cost routes installed does not mean traffic is shared. It means traffic is hashed. ECMP is load spreading, and only if the sources are spread.

💭 THINK FIRST · FAILURE

Two failures arrive in the same week. One takes a hub away entirely. The other leaves everything up, Full, and unchanged — and degrades exactly half the user population. Only one of them is a routing problem.

  • A hub is lost. How long is the outage, and what event ends it?
  • Nothing is down and half the users are suffering. What does "exactly half" tell you?
Q1 — MODEL ANSWER
It depends how the loss is detected. Tunnel interface down is an immediate topology event — neighbour dropped, SPF reruns, route withdrawn, seconds. Tunnel up but hellos stopped means waiting the 40-second dead interval. BFD reduces that to sub-second. Sessions on the failed next hop are torn down and rebuilt on the survivor; a FIB change is one of only two things that re-evaluates a session.
Q2 — MODEL ANSWER
The population splits along the ECMP hash boundary, so the fault is per-path, not per-user or per-application. One path is Alive but not Good. OSPF's only liveness test is whether a neighbour answers hellos — a tunnel with 400 ms latency and 8% loss answers them perfectly.

FortiOS CLI — BFD
config router bfd
    config neighbor
        edit 10.99.1.1
            set interface "Fisheries-Tuggers"
        next
    end
end

config router ospf
    set bfd enable                    <-- process-wide
    config ospf-interface
        edit "Fisheries-Tuggers"
            set bfd enable            <-- or per-interface
        next
    end
end
  • BFD is a detection mechanism, not a routing protocol. It does not choose paths; it tells the protocol sooner that one is gone. OSPF, BGP and static routes can all subscribe.
  • BFD is the scalable alternative to shortening hello/dead timers, which costs CPU and multiplies badly on a hub with many spokes.
  • 40 s beats 180 s. OSPF's dead interval is far more aggressive than BGP's default hold timer (keepalive 60 / hold 180) — which is why a silent hub loss on the overlay was a three-minute problem and this is a forty-second one.
The failure routing cannot see. A tunnel with 400 ms latency and 8% loss answers hellos perfectly. Adjacency stays Full, cost stays unchanged, SPF never reruns, the route never withdraws. BFD does not help — BFD detects dead, not degraded. Detection speed and quality measurement are different problems and exam questions blur them deliberately.

The fix is a different layer. The Fisheries tunnels become SD-WAN members with health checks, so the two paths can be measured and judged. Note the dependency: this only works because OSPF already put both hubs in the FIB.

The two layers, in order
OSPF equal-cost  -->  two FIB next hops  -->  two eligible SD-WAN members
                                                        |
                                        SLA health check measures both
                                                        |
                                 rule selects one that is Alive AND Good
Where the fix goes: the Fisheries core is the spoke side — static tunnels, net-device enable — so its tunnels can be SD-WAN members. On the hubs, dial-up tunnels with net-device disable cannot. That asymmetry is why SD-WAN goes on the Fisheries box, not on Tuggers.
🧠
MENTAL NOTE
Full ≠ good. Liveness is not quality. Routing fills the room; SD-WAN picks from it. ECMP is the prerequisite for member eligibility, not an alternative to it.

💭 THINK FIRST · BOUNDARY

Both hubs redistribute in both directions. Tuggers pushes Perth's LAN into OSPF as an external; Fisheries floods area 0; Gunners is in area 0 too. Nobody has configured a preference anywhere — and that is precisely the danger.

  • What does Gunners do with the prefix it just heard in OSPF, and why is that worse than a routing loop?
  • Tagging stops the leak. What stops the leak when the tagging is wrong?
Q1 — MODEL ANSWER
Gunners already holds Perth's LAN via iBGP at AD 200. The OSPF copy arrives at AD 110 and wins. Gunners installs the path through Fisheries and abandons the overlay. Department traffic for a Department site now transits a third party, outside our IPsec, outside SLA measurement, outside the SD-WAN rules and outside FortiAnalyzer's picture.
Q2 — MODEL ANSWER
Distance. Raise the distance of OSPF externals at the hubs above iBGP's 200, so that even an untagged leak cannot beat the overlay. Filter for correctness; distance for survivability.
SECTION 05

The Redistribution Boundary and Its Contract

A safe boundary has three properties: a known set (prefix-list on import), a marked origin (tag on export, deny on re-import), and deliberate preference where there is a reason for one.

TuggersGunners
BGP → OSPFset tag 10set tag 20
OSPF → BGPmatch tag 20 → deny
(else permit)		match tag 10 → deny
(else permit)
Safety netOSPF external distance raised above 200 at both hubs

Per-hub tags rather than a single "crossed the boundary" tag buys diagnostic value: during an incident you can tell which border a prefix crossed, not merely that it crossed one.

Filter for correctness, distance for survivability. Tagging is the intended mechanism. Raised distance is what saves you when a tag is lost, misconfigured, or a third border appears that nobody told you about.
The failure class that has no alarm. Fisheries adds a twelfth site. OSPF is Full, the prefix is in their area 0 database, and Department branches cannot reach it. Nothing failed — the prefix-list is denying it, which is the prefix-list working correctly. The symptom is an absence, and it is found by a user, not by a system. Exactly the shape of Darwin's Rev 27.
🧠
MENTAL NOTE
Prefer policy that expresses a rule over policy that enumerates a state. Where you must enumerate, write down who reviews it and when — or it becomes the next Rev 27.

💭 THINK FIRST · EXAM & TRAPS

Most of this episode's exam value is in distinctions rather than commands: which layer owns which decision, and which default silently prevents the behaviour you assumed.

  • When is E1 the right answer and when is E2? What decides?
  • Before installing a routing change through FortiManager, what has to be true of the target device?
Q1 — MODEL ANSWER
Which layer owns the decision. If SD-WAN is to judge quality, you want E2 at equal cost so both hubs stay eligible. If routing itself must prefer the nearer hub, E1 — one next hop, no ECMP. Set the same type on both ASBRs: E1 always beats E2 regardless of metric.
Q2 — MODEL ANSWER
Config Status must read In Sync. Install Preview diffs FortiManager's device database against what the device will run — it is only truthful if that stored copy still matches the box. Out-of-Sync means the preview is fiction and the install overwrites out-of-band changes; retrieve and reconcile first.

Common Mistakes

  • Assuming two arrows means half each. ECMP hashes; it does not share. One busy source pins one path.
  • Fixing a utilisation complaint with OSPF cost. Unequal cost removes the second FIB next hop and silently destroys SD-WAN eligibility and failover.
  • Reaching for BFD to solve a degradation. Wrong layer. BFD fixes 40 seconds; it does not fix 8% loss.
  • Setting metric-type on one ASBR only. Looks like a working preference until you check.
  • Treating "Full adjacency" as proof the path is usable. It proves only that hellos are answered.
  • Installing over an Out-of-Sync device. The preview is truthful only about FortiManager's copy of the box.
