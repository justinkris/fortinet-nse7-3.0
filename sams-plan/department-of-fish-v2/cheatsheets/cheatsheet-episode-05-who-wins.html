The single biggest gap closed this episode: sla_map is scoped to exactly one session and exactly one member — the member that session is currently pinned to. It is not a comparison table across every member in the zone.

Reading the bitmask: bit position = SLA target index. Rightmost bit (LSB) = target 1, next bit = target 2, and so on. 1 = SLA target met, 0 = unmet. Example: sla_map=0x2 → binary 10 → target 1 unmet, target 2 met.

Exam tip: if a question asks "does sla_map tell you how the other member is doing," the answer is always no — that's what health-check is for.
🧠
MENTAL NOTE
sla_map = one session's memory of one member's compliance at birth. health-check = the live truth about every member, right now. Never confuse a memory for a live feed.
SECTION 02

Re-Evaluation Triggers — Disappear vs Return

EP-03's two triggers apply identically to a full outage, not just a degraded SLA target: manual clear, and FIB/route change. Tuggers going fully offline withdraws its routes from the FIB — that's the second trigger firing, at outage scale.

The asymmetry that trips people up: a route disappearing triggers re-evaluation. A route reappearing does not. There is no "something better just showed up" trigger — only "what I'm using just vanished."
EventExisting session affected?Why
Tuggers goes offlineYes — torn down, new session births on next packetFIB/route-change trigger fires
Tuggers comes back onlineNo — session stays on GunnersNo trigger exists for a route reappearing
Existing TCP session ends (RST/FIN)N/A — session naturally endsNormal session lifecycle, not a re-evaluation event
New session after Tuggers returnsFresh SD-WAN decision madeRule always re-evaluates at session birth

Business translation: traffic does not snap back all at once when Tuggers returns. It trickles back gradually, one session at a time, as each existing session naturally ends (TCP RST/FIN, or an admin clear) and its replacement is born fresh against whichever members are eligible at that moment.

🧠
MENTAL NOTE
Only disappearance forces re-evaluation. Return just adds an option for the next session born — it never reaches back and grabs an existing one.
SECTION 03

Best Quality & Lowest Cost — The Two-Stage Model

⚠ Needs Reinforcement

Both strategies share the same two-stage shape, and this is the part that wobbled twice in this episode's exam set — once on each strategy. Treat it as the priority item to retest.

1
SLA compliance filters the eligible pool. A member failing its configured SLA target(s) is excluded from consideration — full stop — regardless of strategy.
2
The configured tiebreaker decides among survivors. Best Quality: exactly one configured link-cost-factor metric — never a blended score. Lowest Cost: each member's static, admin-assigned cost value.
⚠
The one exception: if every eligible member fails every configured SLA target simultaneously, Lowest Cost skips stage 1 entirely and cost alone decides — compliance disregarded completely, only in this specific total-failure case.
StrategyTiebreakerWhere configuredSLA still checked?
Best Quality SLASingle link-cost-factor metric (latency / jitter / packet-loss / one composite option)Rule itself (config system sdwan → service)Always filters first
Lowest Cost SLAStatic per-member cost valueMember object (config system sdwan → members)Filters first, EXCEPT total-failure case
Exam trap #1: "Lowest Cost always picks the cheapest member" — False. Cost only decides among SLA-compliant survivors, unless literally every member is failing every target.
Exam trap #2: "link-cost-factor can combine jitter + packet-loss for a holistic score" — False. Exactly one metric (or one named composite option) is chosen; there is no live blending of several metrics.
Configuration split — three separate places
config system sdwan
    config health-check
        edit "teams-hc"
            set server "worldaz.tr.teams.microsoft.com"
            set sla-fail-log-period 10
            config sla
                edit 1
                    set jitter-threshold 30
                    set packetloss-threshold 1
                next
            end
            set members 1 2
        next
    end
    config members
        edit 1
            set cost 5      <- static, used by Lowest Cost only
        next
        edit 2
            set cost 20
        next
    end
    config service
        edit 1
            set mode sla
            set strategy best-quality
            set link-cost-factor jitter   <- single metric, Best Quality only
            set health-check "teams-hc"
        next
    end
end

Why jitter for Teams: real-time voice/video is far more sensitive to variable delay between packets (jitter) than to a flat, consistent latency — jitter causes talk-over and choppy audio, which is the specific symptom that matters for this traffic type.

🧠
MENTAL NOTE
Filter first, then decide. Neither strategy is "holistic" — Best Quality picks one metric, Lowest Cost picks one static number. Compliance always gates the pool, except Lowest Cost's total-failure escape hatch.
SECTION 04

Troubleshooting Workflow — Proving the Model

  1. Confirm the session is explicit-rule matched. diagnose sys session list — presence of sdwan_mbr_seq / sdwan_service_id / sla_map confirms explicit-rule handling (EP-04).
  2. Read sla_map for that one member's history. Bit position = target index, 1 = met. Remember: this tells you nothing about any other member.
  3. Cross-check against the live view. diagnose sys sdwan health-check — confirms current, all-member compliance right now, independent of any session.
  4. If a member vanished, confirm the FIB. diagnose firewall proute list — vwl_service/vwl_mbr fields, route ID > 65535 for SD-WAN-derived routes (EP-04).
  5. Predict, don't assume, on recovery. A returning member does not reclaim existing sessions — only future session births see it as an option.
Remember: config-state commands (get system interface) are not live throughput or compliance evidence — always reach for the diagnose-family command for real-time truth.
