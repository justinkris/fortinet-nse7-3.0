Section 01 · The Big Picture

The Component Tree

FortiManager is three stacked management layers. The global ADOM sits on top and wraps everything. Each ADOM is a self-contained virtual instance holding exactly two databases — a device layer and a policy layer. Every feature in the product belongs to one of those two databases (a few can write to both). The tags show where each leaf lands: Device Policy Both

  • Header & footer policy packages — envelop each ADOM's own policies (carrier / MSSP pattern)
  • Assign vs auto-install to ADOM devices
  • Version reach: same version + two back (7.6 global → 7.4, 7.2 ADOMs)

Mental Model
Global wraps ADOMs. ADOMs hold two databases. Features feed one database or the other — and the database a feature feeds tells you which install operation ships it to FortiGate.
Section 02 · The Confusion Killer

Device Layer vs Policy Layer

This split is where most of the confusion lives, because the GUI panes don't say "layer" anywhere. Use this test: does the feature configure the box, or the traffic decisions? Box settings (interfaces, routing, system, templates) live in the device layer. Traffic decisions (policies, objects, security profiles) live in the policy layer.

Change in device layer → hits FortiGate directly on device install · Change in policy layer → nothing moves until the policy package installs
The one rule the guide keeps repeating: you can configure policies in the device layer, but don't. Make policy-adjacent changes in the policy layer so the object DB and device DB stay in agreement — policy-layer assignments overwrite the selected revision on install.

Scripts are the special case. The script itself doesn't belong to a layer — its run target does:

Mental Model
Everything flows downhill — policy layer → device DB → FortiGate. Retrieve is the single uphill arrow, and it stops at the device DB. Nothing ever flows uphill into a policy package except an explicit Import.
Section 04 · The Layer Above

The Global ADOM

The global ADOM exists to share one set of objects and enveloping policies across many local ADOMs — the carrier/MSSP pattern where header and footer packages sandwich each customer ADOM's own rules.

  • Global object database — objects carry the reserved g prefix; you can't create your own objects starting with g.
  • Header & footer policy packages — wrap around each ADOM's local policy package.
  • Two distribution modes:
    • Automatically install to ADOM devices — hits the policy layer, device DB, and FortiGate in one shot, but bypasses the installation preview.
    • Assign — updates the policy layer only (status → Modified); you must then install or reinstall to reach the device layer and FortiGate.
  • Version compatibility — global ADOM supports local ADOMs at the same version and two versions earlier (7.6 → 7.4 and 7.2). Keep ADOM firmware matched to the FortiGates inside it.
Same global, many locals: one global ADOM can distribute identical global policies to different local ADOMs — that's the whole point of it.
Section 05 · SD-WAN on FortiManager

The SD-WAN Branch of the Tree

Everything SD-WAN on FortiManager hangs off two entry points — and both slot straight into the layer model from Section 02. Per-device SD-WAN and SD-WAN templates are device-layer constructs. The one bridge to the policy layer: creating a zone in an SD-WAN template automatically creates a matching normalized interface, so your firewall policies can reference it.

Per-Device Management
Device Manager > device > Network > SD-WAN
  • Configure SD-WAN on one FortiGate at a time, then installDevice
  • Use when devices genuinely need different SD-WAN designs
  • Same on-box objects you already know: members, zones, performance SLAs, rules
Central Management — SD-WAN Manager
Enable SD-WAN management per device first
  • SD-WAN Network — devices + health/SLA monitors (map view, per-member latency vs threshold)
  • SD-WAN Templates — the shared source of truthDevice
  • Overlay Orchestration — the guided wizard
  • SD-WAN Rules — rules for one or many devices

Inside an SD-WAN template — the exact same four objects you build on-box, defined once and pushed to every target:

MembersPer-member installation targets: device groups, individual devices, or empty = every device (the 4G-only-on-some-branches pattern) ZonesCreating one auto-creates a normalized interface · optional service-sla-tie-break: cfg-order (default) / fib-best-match / input-device Performance SLAsHeader (probe + members) · SLA targets · link status (alive/dead criteria) · action when inactive (update static routes) RulesSame strategies as on-box; metadata variables supply per-device values (gateways, probe targets — the EP-09 pattern)
Overlay Orchestration generates
Five-step wizard → a consistent template set
IPsec overlay templatesAlways IKEv2 · hub = dial-up server, spokes = dial-up clients · PSK (auto-generated) or Signature · ADVPN legacy or 2.0 BGP templatesAlways IBGP · BGP per overlay (default) or BGP on loopback · optional dynamic BGP · loopback IP for health check SD-WAN templateZone over the overlay interfaces + performance SLAs, wired to the routing above TopologiesSingle hub · dual-hub (primary/secondary or primary/primary) · multi-hub up to 4
Three ways to build the overlay: Orchestration (recommended) · predefined IPsec templates (BRANCH / HUB_IPsec_Recommended) · VPN Manager (legacy — never for new SD-WAN)
Two hard restrictions on overlay templates: all devices configured by one SD-WAN overlay template must live in the same ADOM, and each FortiGate can receive configuration from one overlay template only. And you cannot mix VPN Manager and an overlay template on the same network — pick one.
🧠
Mental Model
The SD-WAN template is just a provisioning template — device layer, reasserted on every install, template wins on drift (the EP-08 ownership test). The zone is the bridge: it steps across into the policy layer as a normalized interface so policies can reference it.
Section 06 · Where Marks Are Lost

Exam Traps

TrapThe truth
"VPN Manager configures the device layer"No — VPN Manager, AP Manager, and FortiSwitch Manager are policy-layer features. Provisioning templates, Fabric View, and Extender Manager are device-layer.
"Retrieve updates the policy package"Retrieve saves a new device-DB revision only. The policy package is untouched until you explicitly import.
"Templates and the device DB are equals"Provisioning templates take precedence — a CLI template overwrites the device database on install.
"Pre-run CLI templates stay assigned"Pre-run templates auto-detach after quick install (one-shot, ZTP/LTP). Regular CLI templates stay assigned and re-assert on every install.
"Global auto-install still shows a preview"Auto-install to ADOM devices bypasses the preview entirely. Only Assign + install gives you the preview safety net.
"Normalized interface names are pushed as-is"They're mappings, not renames — lan on FortiManager still installs as port4 on the FortiGate, and the names are case-sensitive.
"No ADOMs enabled = no ADOM"You're always in an ADOM. With ADOMs disabled it's just the single default root ADOM, complete with both layers.
"VPN Manager is how you build SD-WAN overlays"VPN Manager is legacy — never use it for a new SD-WAN topology, and it can't coexist with an overlay template on the same network. Overlay Orchestration is the recommended path.
"One overlay template can span ADOMs"All devices in one SD-WAN overlay template must be in the same ADOM, and each FortiGate takes config from one overlay template only.
"Empty installation target = member installs nowhere"Backwards — an empty Installation Target on an SD-WAN template member installs it on every target device.
"You choose EBGP in the orchestrator"The orchestrator always builds IBGP and always IKEv2. Your choices are the topology, PSK vs Signature, ADVPN version, and BGP per overlay vs BGP on loopback.
