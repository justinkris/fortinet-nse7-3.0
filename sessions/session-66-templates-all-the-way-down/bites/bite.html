SESSION 66 · BITE · FORTIMANAGER SD-WAN TEMPLATES

Templates All the Way Down

One mould, seven castings, twelve stamped numbers — and one file that tells you what your estate really looks like.

“Every branch is identical except for the twelve numbers that aren’t.”
Junior meant it as a complaint. Señor heard it as a specification. Five minutes to refresh the whole session.
The one thing to remember

Three fields, and only three

Inside an SD-WAN member, metadata variables are allowed in exactly three settings. If you remember nothing else from this session, remember the list — and remember what is not on it.

SettingWhy it varies per site
Interface MemberPerth’s ISP2 landed on port8, not port2
Gatewayevery carrier handoff is a different next hop
Health-Check Serverthe probe target should suit the site
Not on the list: SLA thresholds. Latency, jitter and packet-loss targets are absolute numbers in FortiOS and are not metadata-capable. If sites need different health judgements, you change where you probe, not the number.
🧠
Mental note
Interface, gateway, server. The mould is shared; only the stamped numbers differ.
Mechanics

Where the numbers live

  • Path: Policy & Objects > Advanced > Metadata Variables
  • Scope: ADOM-level parameters; also available at the Global ADOM for per-ADOM mapping
  • Names: letters, numbers and underscores only
  • Invoke: type $ in a field to open the picker; + creates one inline; the pen icon edits
  • Icon: a magnifying glass with a $ marks every metadata-capable field
  • Values: one default plus a Per-Device Mapping table — the per-device value always wins
  • Bulk: import and export in CSV and JSON; import can also define new variables
IP/Netmask rule (exam bait): subnet and mask must be specified separately. Valid: $(LAN_Subnet)/$(LAN_Mask), $(LAN_Subnet)/255.255.255.0, 10.10.10.0/255.255.255.0. Invalid: a single combined CIDR variable.
The install-day law

A gate, not a delivery van

Hobart has a variable with no default and no per-device mapping. You install to all seven branches.

  • Six install. Hobart alone fails.
  • Nothing is transmitted to Hobart — not a partial config, not a rollback.
  • Why: substitution happens inside FortiManager. It builds a complete candidate config per device; an unresolvable reference aborts that device’s job before the wire.
The FortiGate receives answers, never questions. There is no $(inet2) on Perth’s flash. There is port8. All the intelligence stays upstairs.
Design judgement

Default it, or leave it empty?

The guide says set a default for every variable. Season 3 said an empty default can be a deliberate tripwire. Both are right — the skill is sorting them.

The sorting rule

Default it when a wrong value fails loudly and locally. Leave it empty when a wrong value would be plausible, silent and site-specific.

  • $(inet1) → default port1. Wrong means the link is obviously dead on day one. Right six times out of seven; the seventh maps itself.
  • $(local_probe) → no default. A Sydney address is plausible, installs cleanly, and lets Singapore measure two thousand kilometres of wet string for eleven months.
🧠
Mental note
A silent wrong answer is more expensive than a loud missing one.
Two syntaxes

CLI script and Jinja

CLI script — variables prefixed with $
config system global
    set hostname $(hostname)
end
config system interface
    edit "loopback0"
        set ip $(loopback_ip) 255.255.255.255
    next
end
Jinja script — variables framed with double braces
config system global
    set hostname {{DVMDB.name}}
end
config system interface
    edit "loopback0"
        set ip {{ipmath('10.200.99.0', branch_id)}} 255.255.255.255
    next
end
  • $(var) for CLI scripts · {{var}} for Jinja. Jinja adds Python-like logic such as ipmath.
  • DVMDB.name is a device database variable — native to every managed device, no definition needed.
  • Trap: typing {{ in the editor autocompletes metadata variables only. Device database variables must be typed from memory.
Assembly

Template groups and top-down order

Template typeWhat it carries
SD-WAN templatezones, members, performance SLAs, SD-WAN rules
System templateDNS, admin settings, log settings, SNMP, alert email (importable, clonable, Preview CLI Configuration)
CLI templateraw CLI or Jinja — anything the GUI can’t express or that is variable-heavy

A template group bundles them and is assigned to devices, VDOMs or a device group — one assignment instead of many. Groups may mix CLI and Jinja scripts, applied top-down.

Troubleshooting consequence: later overrides earlier, so the last item in the group silently gets the final word. When a setting won’t stick, read to the bottom of the group — the template you’re staring at may have already lost.
Policy side

Zones, never members

  • Firewall policies for SD-WAN traffic must reference SD-WAN zones, not individual members.
  • Other interfaces in the policy are usually normalized interfaces, mapped per device and resolved at install (LAN → port5 here, port1 there).
  • SD-WAN members do not use normalized interfaces. An IPsec interface used as a member needn’t be normalized; one that isn’t a member must be, so policies can reference it.
  • Creating a zone in an FMG SD-WAN template auto-creates the matching normalized interface.
Two different bugs, don’t merge them. Hard-coding a port breaks at sites cabled differently — a portability bug. Referencing a member breaks at every site the moment SD-WAN fails over: the policy stops matching and traffic is denied, not degraded — a design bug.
The senior habit

Export before you touch anything

Exporting metadata variables gives you a grid: every variable across the top, every device down the side. Filling it in is the obvious use. Reading it is the valuable one.

The export grid is a drift report. It is the fastest answer in the product to “what is actually different between these sites?” Every column is a promise the estate makes; every off-pattern cell is either a known exception (port8 at Perth) or a bug (two branches sharing branch_id 5). Put it in version control and you also learn when and who.
🧠
Mental note
The template is the mould. The file is the estate. Guard the file.
Senior engineering lessons

Seven rules from Session 66

Lesson 01
Probe what the traffic actually uses.
A health check measuring a path your revenue never takes is a dashboard that lies. Choose the probe target from purpose, not from convenience.
Lesson 02
Default it when wrong fails loudly; leave it empty when wrong would be silent.
Emptiness is a legitimate design choice. A missing value stops an install; a plausible wrong value survives for a year.
Lesson 03
Install is a validation gate, not a delivery van.
Resolution happens upstairs, before transmission. One device fails; the rest proceed. Fail loudly beats succeed wrongly.
Lesson 04
Derive when the value is a pure function of a stored identity; store when it’s arbitrary.
A loopback is branch_id plus a prefix — derive it. A carrier gateway came from an email — store it. Derivation buys correctness and costs legibility, so comment the Jinja and keep the seed in the sheet.
Lesson 05
The export grid is a drift report.
One page that answers the question eight sources of truth make unanswerable: what is actually different between these sites?
Lesson 06
Specific beats general — in its third costume.
Per-device value beats default. Later template beats earlier. Same law, new clothes. When two things could set a value, ask which one is more specific.
Lesson 07
Zones, not members.
Referencing a member doesn’t merely hard-code a port — it revokes SD-WAN’s licence to steer. You built a multi-link WAN, then forbade six-sevenths of it.
Sixty-second recall

If you only re-read one box

Interface · Gateway · Health-check server — the only metadata-capable member fields.
Policy & Objects > Advanced > Metadata Variables — where they live; $ invokes; CSV and JSON both ways.
No default and no mapping — that device’s install fails, alone, before anything is sent.
$( ) is CLI, {{ }} is Jinja — and {{ autocomplete hides the device database variables.
Template groups apply top-down — the bottom wins.
SD-WAN policies reference zones — members break on failover; members don’t use normalized interfaces.
