TECHNICAL CONCEPTS COVERED (study guide pp. 23-45)
==================================================================
1. THE THREE METADATA-CAPABLE SD-WAN MEMBER FIELDS (exam-critical, p.24):
   INTERFACE MEMBER · GATEWAY · HEALTH-CHECK SERVER. Nothing else in the member.
   NOTE: SLA THRESHOLDS ARE **NOT** ON THE LIST — student proposed varying thresholds
   per site (good engineering instinct); the product gives you the lever on the SERVER,
   not the number. Senior framing coined: "When the product gives you one lever and your
   design wants another, that is information about the design the vendor expects."
2. METADATA VARIABLES — MECHANICS (pp.25-28). ADOM-level parameters, also available at
   Global ADOM for per-ADOM mapping. Usable in CLI scripts, templates, model devices.
   Path: Policy & Objects > Advanced > Metadata Variables. NAME MAY CONTAIN ONLY LETTERS,
   NUMBERS AND UNDERSCORES. Type $ in a field to invoke the picker; "+" creates a new
   variable inline; pen icon edits. MAGNIFYING-GLASS-WITH-$ ICON marks metadata-capable
   fields. Default value + Per-Device Mapping table; specific beats default.
   IP/NETMASK RULE (p.27, exam bait): subnet and mask MUST be specified SEPARATELY.
   Valid: $(LAN_Subnet)/$(LAN_Mask) · $(LAN_Subnet)/255.255.255.0 · 10.10.10.0/255.255.255.0
   INVALID: one combined CIDR variable.
3. UNRESOLVED VARIABLE AT INSTALL (p.28) — reprise of the Season 3 law, re-derived:
   No default AND no per-device mapping = FortiManager CANNOT install that configuration.
   Six branches install, Hobart alone fails, and the failure is detected BEFORE TRANSMISSION.
   Law restated on glass: "INSTALL IS A VALIDATION GATE, NOT A DELIVERY VAN."
   Mechanism sentence: substitution happens INSIDE FortiManager at install time; a complete
   candidate config is built per device; unresolvable reference aborts THAT DEVICE'S JOB with
   nothing transmitted. "The FortiGate receives answers, never questions."
4. DEFAULT vs TRIPWIRE — the Season 3 "when NOT to abstract" lesson approached from a new
   angle and DERIVED BY THE STUDENT THIS TIME. Guide says "good practice to set a default";
   Season 3 said an empty default can be a deliberate tripwire. Sorting rule coined this
   session (student's reasoning, Señor's wording):
   "DEFAULT IT WHEN A WRONG VALUE FAILS LOUDLY AND LOCALLY. LEAVE IT EMPTY WHEN A WRONG
   VALUE WOULD BE PLAUSIBLE, SILENT AND SITE-SPECIFIC."
   Worked example: $(inet1) default port1 (wrong = obviously broken link, six of seven right);
   $(local_probe) NO default (a Sydney default is plausible, installs fine, and lies for
   eleven months — Riley: "Singapore silently measures wet string").
5. HEALTH-CHECK DESIGN — the student's best moment (see PERFORMANCE). A health check may
   carry MULTIPLE SERVERS: one static corporate target plus one metadata variable resolving
   per site. Guide's own example does exactly this (Corp_HC = one fixed IP + one variable).
   PRINCIPLE COINED BY THE STUDENT: "PROBE WHAT THE TRAFFIC ACTUALLY USES." He argued the
   Sydney probe should STAY because the trading feeds come from Sydney — a better argument
   than the one being fished for (which was local probe targets).
6. IMPORT / EXPORT OF METADATA VARIABLES (p.29). CSV AND JSON, both directions. Export =
   grid of every variable × every device. Import sets values in bulk AND CAN DEFINE NEW
   VARIABLES. Second, senior reason for export taught this session:
   THE EXPORT GRID IS A DRIFT REPORT. It is the fastest answer in the whole product to
   "what is actually different between these sites?" — Thursday's unanswerable question.
   Every column is a promise; every off-pattern cell is either a known exception (port8 at
   Perth) or a bug. Señor: "Junior's template is the mould. THIS FILE IS THE ESTATE."
   Recommendation given: keep the export in version control → you learn WHEN and WHO.
7. DEVICE DATABASE VARIABLES (p.30). Natively available per managed device; Jinja templates
   and scripts have DIRECT access; no need to define metadata variables that duplicate them.
   Example {{DVMDB.name}} for hostname. TRAP: typing {{ in the FortiManager editor shows
   METADATA VARIABLES ONLY — device DB variables must be typed from memory.
8. CLI TEMPLATES AND THE TWO SYNTAXES (pp.34-36). CLI templates push advanced settings and
   anything variable-heavy; FortiManager ENFORCES the content when pushing.
   CLI SCRIPT syntax: $(variable). JINJA syntax: {{variable}}. Jinja gives Python-like logic;
   ipmath('10.200.99.0', branch_id) builds a loopback from a prefix + the branch's number.
   A TEMPLATE GROUP MAY MIX CLI AND JINJA SCRIPTS AND APPLIES THEM TOP-DOWN.
9. DERIVE vs STORE — new senior lesson, built this session:
   "DERIVE WHEN THE VALUE IS A PURE FUNCTION OF AN IDENTITY YOU ALREADY STORE AND THE
   FUNCTION IS STABLE. STORE WHEN THE VALUE IS ARBITRARY."
   loopback_ip and router_id are pure functions of branch_id → derive.
   inet2_gw is whatever the carrier decided in an email → store.
   COST OF DERIVATION = LEGIBILITY. Way A (stored) answers "why this address?" from a cell in
   a spreadsheet; Way B (derived) requires knowing a CLI template exists, finding it, reading
   Jinja, and knowing ipmath. Mitigation: COMMENT THE JINJA and KEEP branch_id IN THE SHEET —
   "the spreadsheet keeps the INPUTS, the templates keep the RULES" (Junior).
10. TEMPLATE GROUPS (p.32) + SYSTEM TEMPLATES (p.33). Template Groups pane: add templates to
    a group, assign the GROUP to devices, VDOMs or a device group instead of assigning
    templates individually. Three template types tabulated this session:
    SD-WAN template (zones, members, performance SLAs, rules) · SYSTEM template (DNS, alert
    email, admin settings, log settings, SNMP; importable from a device, clonable, has
    Assign to Device/Group and PREVIEW CLI CONFIGURATION) · CLI template (raw CLI or Jinja).
    TOP-DOWN ORDER CONSEQUENCE (student derived): later overrides earlier, so the LAST item
    in a group silently gets the final word. Troubleshooting rule: "when a setting won't
    stick, READ TO THE BOTTOM OF THE GROUP — the template you are staring at may have
    already lost." Filed as the THIRD COSTUME of specific-beats-general.
11. POLICY PACKAGES, ZONES AND NORMALIZED INTERFACES (pp.37-39).
    FIREWALL POLICIES FOR SD-WAN TRAFFIC MUST REFERENCE SD-WAN ZONES, NEVER INDIVIDUAL
    MEMBERS. Other interfaces in the policy are normally NORMALIZED INTERFACES with per-device
    (or per-platform) mapping rules resolved at install — guide example LAN → port5 on
    branch1_fgt, port1 on branch2_fgt.
    SD-WAN MEMBERS DO NOT USE NORMALIZED INTERFACES. Therefore an IPsec interface used AS an
    SD-WAN member need not be normalized; an IPsec interface NOT used as a member MUST be
    normalized so policies can reference it (policies are required for the tunnel to come up).
    Creating a zone in a FortiManager SD-WAN template AUTO-CREATES the matching normalized
    interface.
12. TWO DISTINCT FAILURES OF "port instead of zone" (taught as a pair, worth reusing):
    PORT instead of ZONE → wrong at sites cabled differently (a PORTABILITY bug).
    MEMBER instead of ZONE → wrong at EVERY site the moment steering happens (a DESIGN bug):
    the policy stops matching after failover and traffic is DENIED, not degraded. "You built
    a multi-link WAN and then wrote a policy forbidding six-sevenths of it."
13. MENTIONED, NOT TAUGHT / AVAILABLE FOR LATER: SD-WAN zone service-sla-tie-break options
    (cfg-order default · fib-best-match · input-device for overlay stickiness, with
    set input-zone and set tie-break input-device); Performance SLA page anatomy in FMG
    (Header · SLA Target · Link Status · Action When Inactive); importing an existing
    device's SD-WAN settings into a template (p.31); FMG SD-WAN monitor map/table/template
    views. All are legitimate S67+ material.

KEY CLI / GUI PATHS DISCUSSED
==================================================================
Melbourne's real SD-WAN block was used as the working artefact all session:
  config system sdwan
      set status enable
      config zone
          edit "underlay"
      end
      config members
          edit 1
              set interface "port1"      <- becomes $(inet1)
              set zone "underlay"
              set gateway 10.10.5.254    <- becomes $(inet1_gw)
          next
          edit 2
              set interface "port2"      <- becomes $(inet2)   [Perth = port8]
              set gateway 172.20.8.1     <- becomes $(inet2_gw)
          next
      end
      config health-check
          edit "Corp_HC"
              set server "10.100.1.10" "$(local_probe)"   <- static + variable
              set members 1 2
              config sla
                  edit 1
                      set latency-threshold 100
                      set jitter-threshold 30
                      set packetloss-threshold 2
              end
      end
  end

CLI SCRIPT (metadata variables with $):
  config system global
      set hostname $(hostname)
  end
  config system interface
      edit "loopback0"
          set ip $(loopback_ip) 255.255.255.255
      next
  end

JINJA SCRIPT (metadata variables with {{ }}, device DB variables typed manually):
  config system global
      set hostname {{DVMDB.name}}
  end
  config system interface
      edit "loopback0"
          set ip {{ipmath('10.200.99.0', branch_id)}} 255.255.255.255
      next
  end

GUI paths:
  Policy & Objects > Advanced > Metadata Variables      (create/edit/default/per-device map)
  Policy & Objects > Advanced > Metadata Variables > export/import (CSV | JSON)
  Device Manager > Provisioning Templates > Template Groups
  Device Manager > Provisioning Templates > System Templates ( > Preview CLI Configuration )
  Device Manager > Provisioning Templates > CLI Templates
  SD-WAN Manager > SD-WAN Templates
Metadata-capable fields are marked by a MAGNIFYING GLASS WITH $; type $ to open the picker.

EXAM-RELEVANT NOTES
==================================================================
- Metadata variables in an SD-WAN member: INTERFACE MEMBER · GATEWAY · HEALTH-CHECK SERVER.
- Path: Policy & Objects > Advanced > Metadata Variables. Names: letters, numbers, underscores.
- Magnifying-glass-$ marks capable fields; type $ to invoke; + creates inline.
- IP/Netmask must be given as SEPARATE subnet and mask; a single combined variable is invalid.
- No default AND no per-device mapping = install fails FOR THAT DEVICE ONLY; others proceed;
  nothing is transmitted to the failed device.
- Import/export of metadata variables: CSV AND JSON, both directions; import can DEFINE NEW
  VARIABLES; export lists every variable and its value per device.
- Device database variables (e.g. DVMDB.name) are native, need no definition, are directly
  accessible to Jinja, and are NOT offered by the {{ autocomplete.
- CLI script syntax = $(var). Jinja syntax = {{var}}. Jinja adds logic (ipmath).
- Template groups can MIX CLI and Jinja scripts and apply them TOP-DOWN (later wins).
- Template groups may be assigned to devices, VDOMs, or a device group.
- System template covers DNS, alert email, admin settings, log settings, SNMP; importable from
  a managed device; clonable; has Assign to Device/Group and Preview CLI Configuration.
- SD-WAN firewall policies MUST reference SD-WAN ZONES, not members.
- SD-WAN members do NOT use normalized interfaces; other policy interfaces usually DO.
- An IPsec interface used as an SD-WAN member need not be normalized; if not used as a member,
  it MUST be normalized to be referenced in policies (policies required for tunnel to come up).
- Creating a zone in an FMG SD-WAN template auto-creates the matching normalized interface.
- SD-WAN zone settings: Name · Interface Members (>=1 to steer) · optional service-sla-tie-break
  (cfg-order default | fib-best-match | input-device for overlay stickiness).
