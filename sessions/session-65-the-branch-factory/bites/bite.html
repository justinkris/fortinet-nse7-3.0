SESSION 65 · BITE · FORTIMANAGER FOR SD-WAN

One Firewall Is a Pet. Eight Is a Factory.

Five minutes on FortiManager for SD-WAN: layers, templates, targets, and the four things you must decide before the wizard.

Eight sources of truth is the same as no source of truth.
The value of FortiManager is not that it saves typing. It is that it lets you answer the only troubleshooting question that matters at scale — what is different?
The One Idea

Drift, and the cure for drift

Eight branches managed by hand through eight GUIs start identical and end as cousins. Each individual change is small, local, probably even correct. Cumulatively they destroy your ability to compare two sites — and they leave no diary for the auditor.

FortiManager's answer is one source of truth, pushed outward: shared templates for structure, per-device variables for numbers, revision history for accountability.

Analogy
Pet vs Factory
One firewall is a pet — you feed it, you know its noises, affection scales fine. Eight firewalls is a factory. Factories do not survive on affection. Factories have foremen, and the foreman is software.
Architecture

Three management layers

FortiManager layers — top to bottom
GLOBAL ADOM
  · global object database
  · HEADER + FOOTER policy packages  → envelop each ADOM's policies
    (carrier use: customer traffic crosses the network,
     never reaches carrier infrastructure)

ADOM
  · policy packages (create, manage, install)
  · ONE COMMON OBJECT DATABASE per ADOM
    (addresses, services, security profiles)
  · groups devices for admins to monitor/manage

DEVICE MANAGER
  · per-device database: name, type, model, IP,
    firmware, revision history, real-time status
  · install to ONE device or MANY simultaneously

When do you need a second ADOM? Multi-tenancy / MSSP customer isolation · regulatory or regional separation · different FortiOS firmware versions (an ADOM binds to a version).

Cost of splitting: the common object database is per ADOM. Two ADOMs means maintaining your address objects twice — which is drift wearing a suit. LoFinance runs one company, one admin team, one ADOM.
Design decision

Per-device vs central management

WhereDevice Manager > device > Network > SD-WANSD-WAN Manager > SD-WAN Templates

The GUI pages look almost identical either way, and both offer the same three sections you know from FortiGate: SD-WAN Zones, Performance SLA, SD-WAN Rules.

🧠
Mental note
Stay in central management as long as the differences can be expressed as installation targets or metadata variables. Fall back to per-device only when a site is structurally its own animal.
The escape hatch

Installation targets

Every SD-WAN member inside a template carries its own Installation Target. Empty means install everywhere. Populated with a device group or specific devices means install only there — and on every other device that member simply does not exist. Not disabled. Absent.

One template, seven branches, two with MPLS
SD-WAN template members
  port1 (ISP1)  →  Installation Target: [ empty ]      → every branch
  port2 (ISP2)  →  Installation Target: [ empty ]      → every branch
  port4 (MPLS)  →  Installation Target: [ main-sites ] → Melbourne + Brisbane only
Senior habit: name groups, not devices. When Auckland buys MPLS next year you add it to the group and never touch the template. A template full of named exceptions has stopped being a template.
Before the wizard

Four things you must decide

Network planning — SD-WAN overlay template
1. Topology type                              (single hub / dual hub / multiregion)
2. Overlay network address space
3. Loopback IP address space
4. BGP AS number for the SD-WAN overlay region

And the prerequisites — separate from the decisions above:

  • Hubs must already exist as FortiManager-managed devices — model devices or discovered — with links and interfaces configured
  • Devices preconfigured with admin settings and interface IP/subnet, then imported
  • A device group containing the branches must exist before you proceed
🧠
Mental note
Configuration you can change on a Tuesday. Planning you change by starting over.
Sequence

Six steps, and the one everybody skips

SD-WAN overlay deployment
1  Define network topology and subnets
2  Preconfigure network + SD-WAN devices (admin, interface IP/subnet)
3  Import devices to FortiManager
4  Run the SD-WAN overlay orchestration wizard
5  REVIEW the generated configuration templates  ← skipped by everyone
6  Install configurations on devices

   (branches can be added to the branch device group later)

The wizard generates SD-WAN, IPsec, BGP and CLI templates, grouped by device with assignment done for you, using Fortinet's recommended settings. Step 5 is where you read what it inferred on your behalf before it becomes real.

Blast radius × remoteness. Locally, a bad install is an inconvenience. Remotely, the recovery path travels over the thing you just changed — and a template pushes to a group, so it happens to seven sites at once, at the speed of software.
Restrictions: all devices under one overlay template must be in the same ADOM · each FortiGate accepts config from one overlay template only · you cannot use VPN Manager and an SD-WAN overlay template on the same network (for new deployments, use the overlay template).

Trap: SD-WAN management must be enabled per device before that device appears in SD-WAN Manager. "The branch isn't showing up" is usually this — not an ADOM problem.

The four Device Manager wizards:

  • Add Device — bring a device under management and import its configuration
  • Import Configuration — pull interface mappings, policy database and objects up into a policy package (runs with Add Device by default; re-runnable via right-click)
  • Install Wizard — push changes down, with a preview you can cancel
  • Re-install Policy — quick policy-package re-push, also with preview (right-click)
🧠
Mental note
Import comes up. Install goes down. Confuse them under pressure and you overwrite the branch with the template — or the template with the branch.
Carried forward

Debt from Session 64 — the mechanism

config system global
config system global
    set snat-route-change {enable | disable}    # disable = DEFAULT

ROUTING CHANGE OCCURS →
    enable   → existing SNAT sessions: STAMPED dirty       (rip the bandaid)
    disable  → existing SNAT sessions: NOT STAMPED         (keep old route
                                                            until expiry)

Mechanism, not consequence: the setting decides whether existing SNAT sessions receive the dirty stamp. Dropped calls and rebuilding applications are downstream weather. Exam questions describe the weather and ask you for the stamp.

The part that outlives the exam

Senior engineering lessons

  • Eight sources of truth = no source of truth. Templates aren't about typing. They exist so you can still answer "what is different?" in year three.
  • Express difference as targets and variables before you abandon the shared model. Two templates with a naming convention is still drift.
  • Name groups, not devices. It costs nothing today and saves the template from becoming a list of exceptions.
  • Know whether you are making a planning decision or a configuration decision. One you revise on a Tuesday; the other you revise by starting over.
  • Blast radius × remoteness. Always preview. A green tick is not a review — it is the moment you find out what you actually asked for.
  • The wizard has excellent taste and no judgement. It will build precisely what you describe, beautifully, eight times.
  • Answer budget questions with what it would take. Not "yes", not "it depends" — the design, the constraint, and the cost. That is how "can one person run eight sites?" becomes "one person plus one foreman."
