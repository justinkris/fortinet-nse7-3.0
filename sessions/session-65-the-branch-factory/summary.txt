==================================================================
BUSINESS PROBLEM
==================================================================
Scale from one managed firewall to eight, with one engineer, from Sydney, with no travel
budget. The real risk is NOT effort — it is CONFIGURATION DRIFT: eight sources of truth = no
source of truth, so the question "what is different?" becomes unanswerable, and no audit
trail exists. Solution: FortiManager as the management plane.

TECHNICAL CONCEPTS COVERED (study guide pp. 5–22)
==================================================================
1. WHY FORTIMANAGER (derived by student, not given). Danger of eight pets is not typing —
   it is DRIFT. Twins at birth become cousins (Riley's line). Templates kill drift by
   creating ONE source of truth pushed outward. Revision history answers "who changed what".
2. FORTIMANAGER SD-WAN CAPABILITIES (guide list): provision SD-WAN templates / CLI templates /
   firewall policies across many devices; configure SD-WAN per-device; monitor SD-WAN status;
   central repository for config revision control + security audits; deploy & monitor complex
   IPsec overlay topologies; guided overlay orchestration with BGP; zero-touch provisioning;
   scripts and JSON APIs for automation. (FortiAI on FortiManager mentioned in guide p.10 —
   licensed, up to 3 LOCAL admins only — NOT taught this session, available for S66+.)
3. THREE MANAGEMENT LAYERS (student built the middle, was given top/bottom):
   GLOBAL ADOM  → global object DB + HEADER and FOOTER policy packages that ENVELOP each
                  ADOM's policies. Carrier use case: customer traffic traverses the carrier
                  network but cannot reach carrier infrastructure.
   ADOM         → policy packages + ONE COMMON OBJECT DATABASE per ADOM (addresses, services,
                  security profiles). ADOMs group devices for admins to monitor/manage.
   DEVICE MGR   → per-device database: name, type, model, IP, firmware, revision history,
                  real-time status.
   Install can target a single FortiGate or many simultaneously.
4. WHEN TO SPLIT ADOMS (student gave the principle "admin boundaries"; Señor made it concrete):
   (a) MSSP / multi-tenant customer isolation, (b) regulatory or regional separation,
   (c) FIRMWARE VERSION — ADOMs bind to a FortiOS version. LoFinance = ONE ADOM, because the
   common object DB is per-ADOM and splitting duplicates objects = "drift wearing a suit."
5. TWO SD-WAN CONFIG APPROACHES.
   PER-DEVICE: Device Manager > click device > Network > SD-WAN. For devices with DIFFERENT
   SD-WAN requirements that must be maintained separately.
   CENTRAL: SD-WAN templates assigned to devices/groups; change the shared template once and
   install pushes to all targets. Reduces administrative overhead for similar devices.
   Pages look ALMOST IDENTICAL either way; same three sections as FortiGate GUI (SD-WAN Zones,
   Performance SLA, SD-WAN Rules). Metadata variables usable in Interface Member, Gateway,
   Health-Check Server — CENTRAL/template path only.
   SENIOR RULE COINED THIS SESSION: "Stay in central management as long as the differences can
   be expressed as TARGETS or VARIABLES. Fall back to per-device only when a site is
   structurally its own animal."
6. INSTALLATION TARGETS (per SD-WAN MEMBER inside a template). Empty = install on every
   device. Populated (device group or individual devices) = install only there. Guide example
   reproduced: port1(ISP1)/port2(ISP2) empty → all branches; port4(MPLS) → "main" group only.
   Non-target devices get NO port4 at all — not disabled, not present.
   SENIOR HABIT: name GROUPS, not devices, so future MPLS additions never touch the template.
7. METADATA VARIABLES (introduced, deferred to S66). ADOM-level parameters, also at Global
   ADOM for per-ADOM mapping; usable in CLI scripts, templates, model devices. Student
   re-derived the need unprompted ("a variable for that port, changes depending on device").
   Callback to Season 3 certificate work.
8. TWO DOORS TO SD-WAN IN FORTIMANAGER.
   Device Manager > Provisioning Templates — classic path, good for customers ALREADY running
   SD-WAN and bringing it under management.
   SD-WAN Manager — SD-WAN Network (devices + monitors) · SD-WAN Templates · SD-WAN Overlay
   Orchestration (wizard) · SD-WAN Rules (one or more devices).
   TRAP TAUGHT: SD-WAN management must be ENABLED PER DEVICE before it appears in SD-WAN
   Manager. ("Riley will one day tell you a branch isn't showing up.")
9. FOUR DEVICE MANAGER WIZARDS + DIRECTION OF TRAVEL (Señor's framing):
   Add Device (bring under management + import config) · Import Configuration (interface
   mappings, policy DB, objects UP into a policy package; runs with Add Device by default,
   re-runnable by RIGHT-CLICK on the managed device) · Install Wizard (push DOWN with
   preview + cancel) · Re-install Policy (quick policy-package re-push, with preview;
   also right-click). "IMPORT COMES UP, INSTALL GOES DOWN."
10. OVERLAY TEMPLATE PLANNING — FOUR ELEMENTS (exam-critical, guide p.17):
    (1) Topology type  (2) Overlay network address space  (3) Loopback IP address space
    (4) BGP AS number for the SD-WAN overlay region.
    PLUS the prerequisites: hubs must exist as managed devices (real or MODEL devices) with
    links/interfaces configured; branch devices may be defined now or later BUT the BRANCH
    DEVICE GROUP MUST EXIST before proceeding.
11. SIX-STEP OVERLAY DEPLOYMENT SEQUENCE: 1 define topology/subnets · 2 preconfigure network
    and devices (admin settings, interface IP/subnet) · 3 import devices to FortiManager ·
    4 run the overlay orchestration wizard · 5 REVIEW generated templates and fine-tune ·
    6 install to devices. More branches can be added to the branch group later.
12. WHY STEP 5 EXISTS (student derived half; Riley supplied "no travel budget"):
    "BLAST RADIUS × REMOTENESS." On a local box a bad install is an inconvenience; on a remote
    branch the RECOVERY PATH TRAVELS OVER THE THING YOU JUST CHANGED — and a template pushes
    to a GROUP, so it happens to seven sites simultaneously at the speed of software.
    Second reason: the wizard INFERS. It generates SD-WAN, IPsec, BGP and CLI templates
    grouped by device with assignment done for you. Junior: "So step 5 is where you find out
    what you actually asked for." (Junior's best line to date.)
13. OVERLAY TEMPLATE RESTRICTIONS (given, memorisation): all devices under one overlay
    template must be in the SAME ADOM; each FortiGate can receive config from ONE overlay
    template only; multiple overlay templates per ADOM and per FortiManager are allowed for
    multiple topologies. CANNOT use VPN Manager and an SD-WAN overlay template for the same
    network — for new deployments use the overlay template.
14. MENTIONED, NOT TAUGHT (banked): single-hub → dual/multi-hub conversion WITHOUT recreating
    components; ZTP (S67-ish, guide Lesson 02); monitoring dashboards (bandwidth, latency,
    jitter, packet loss); FortiAI on FortiManager.

EXAM-RELEVANT NOTES
==================================================================
- Per-device mgmt = different SD-WAN requirements per device, edited on the device's SD-WAN
  page. Central mgmt = templates → device/group, reduces admin overhead. Metadata variables
  in Interface Member / Gateway / Health-Check Server are the CENTRAL-management tell.
- Installation Target is a property of an SD-WAN MEMBER. Empty = every device.
- FOUR planning elements before an overlay template: topology type · overlay network address
  space · loopback IP address space · BGP AS number for the overlay region.
- Prerequisites: hubs defined as managed devices (model or discovered) with links/interfaces;
  BRANCH DEVICE GROUP must exist before proceeding.
- Overlay template restrictions: same ADOM for all devices; ONE overlay template per FortiGate;
  multiple templates per ADOM allowed; branches addable later; VPN Manager and overlay template
  are MUTUALLY EXCLUSIVE for the same network.
- Layers: Global ADOM (global object DB + header/footer policy packages) → ADOM (policy
  packages + ONE common object DB) → Device Manager (per-device DB, revisions, status).
- Four wizards: Add Device · Import Configuration (UP) · Install Wizard (DOWN, preview) ·
  Re-install Policy (preview). Import Configuration and Re-install Policy open by RIGHT-CLICK.
- SD-WAN Manager sections: SD-WAN Network · SD-WAN Templates · SD-WAN Overlay Orchestration ·
  SD-WAN Rules. SD-WAN management must be ENABLED PER DEVICE to appear there.
- Six-step deployment; step 5 (review generated templates) is non-optional.
